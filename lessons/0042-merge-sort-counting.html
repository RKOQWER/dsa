Merge Sort as a Counting Tool — the merge step sees every cross-pair exactly once

You know merge sort as a sorting algorithm. This lesson teaches it as a counting algorithm. The key observation, which unlocks an entire class of hard problems: when merge sort merges two sorted halves, it compares every left element against every right element in O(n) total — and that is precisely the information needed to count pairs with some cross-half relationship. Problems that ask "for each element, how many elements to its right are smaller?" or "count pairs (i, j) where i < j and nums[i] > 2·nums[j]" become O(n log n) once you realize the merge step is already doing the cross-pair sweep you need; you just have to record the count instead of discarding it. This pattern is the reason merge-sort-based solutions exist for problems that look like they need O(n²) comparisons.

Warm-up — recall (no peeking)

1. In standard merge sort, the merge step takes two sorted arrays of total size m and produces one sorted array. Why is the total work across ALL merge steps O(n log n) and not O(n²)?
2. Binary search (Lesson 10) in a sorted array of size m costs O(log m). If you have a sorted right-half of size m and you binary-search for each of the n/2 left elements, what is the total cost, and how does that compare to a linear scan over the sorted right-half for each left element?

Deriving the pattern via Inversion Count

An inversion in an array is any pair of indices (i, j) where i < j but nums[i] > nums[j] — an element that is to the left but larger. The question: count all inversions. Count of Smaller Numbers After Self (LC 315) asks essentially the same thing per element.

Derive it

Brute force: for every pair (i, j) with i < j, check if nums[i] > nums[j]. Two nested loops — O(n²). With n = 10⁵ that is 10¹⁰ operations; completely infeasible.

Spot the waste. The brute force re-examines pairs it already has partial information about. If you know nums[3] > nums[7], and you later know nums[3] > nums[6], you're doing separate work that could have been bundled. But the deeper observation is this: what structure would make it cheap to count "how many elements on the right are smaller than nums[i]?" If the right side were sorted, a binary search would answer it in O(log n). And if the left side were also sorted, a single two-pointer pass would answer it for all left elements in O(n).

The insight (= the pattern). Merge sort recursively sorts both halves before merging them. By the time the merge step runs, the left half and right half are already sorted — that's exactly the structure you just said you needed! So: run the normal merge sort, but during the merge step, before (or while) you merge, count the cross-inversions using the sortedness of the two halves. When a left element left[i] is placed into the output (because left[i] ≤ right[j]), j right elements have already been moved out before it — meaning j right elements are smaller than left[i] and came after it. That is a count of j inversions contributed by left[i], computed for free during the merge sweep.

Why this doesn't over-count. Every inversion spans exactly one merge step: the two elements are in the same half at some recursion level and in different halves at the level above. So each inversion is counted exactly once, at the level where the two elements first appear in different halves. The total count is the sum of all cross-inversion counts across all merge steps.

def count_inversions(arr):
    """Returns (sorted copy of arr, number of inversions in arr).
    Inversion: pair (i,j) with i < j and arr[i] > arr[j]."""
    if len(arr) <= 1:
        return arr[:], 0
    mid = len(arr) // 2
    left,  lc = count_inversions(arr[:mid])
    right, rc = count_inversions(arr[mid:])

    # ---- merge step: count cross-inversions ----
    merged, cross = [], 0
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            # left[i] stays left: j right elements already moved out are all < left[i]
            # those j elements came AFTER left[i] in the original array, so j inversions
            cross += j
            merged.append(left[i]); i += 1
        else:
            # right[j] < left[i]: it goes first; no count here
            # (we count when we finally place the left elements that beat it)
            merged.append(right[j]); j += 1
    while i < len(left):
        cross += j          # all of right was already placed; j = len(right)
        merged.append(left[i]); i += 1
    merged += right[j:]
    return merged, lc + rc + cross

You didn't recall "modified merge sort for inversions" — you asked "what structure makes the count cheap?", answered "sorted halves", and then realized merge sort hands you exactly that structure at every level. The counting is free; you're just reading off a number that the merge was computing anyway.

The three variants — same bones, different counting predicate

Every merge-sort counting problem has the same skeleton: sort both halves recursively, then during the merge step exploit the sortedness to count cross-half pairs satisfying some relation. The only thing that changes between problems is what relation you're counting and whether you count while merging or just before merging.

Variant 1 — Count of Smaller Numbers After Self (LC 315)

"For each i, how many j > i have nums[j] < nums[i]?" — a per-element inversion count instead of a global total. The trick: carry each element's original index through the merge so you can write the count back to the right position in a result array. When a left element left[i] is placed (meaning left[i] ≤ right[j]), exactly j right elements were placed before it, all smaller — so add j to result[original_index_of_left[i]].

def countSmaller(nums):
    result = [0] * len(nums)
    # carry (original_index, value) so we can write back to result
    indexed = list(enumerate(nums))

    def merge_sort(arr):
        if len(arr) <= 1:
            return arr
        mid = len(arr) // 2
        left  = merge_sort(arr[:mid])
        right = merge_sort(arr[mid:])
        merged = []
        i = j = 0
        while i < len(left) and j < len(right):
            if left[i][1] <= right[j][1]:
                result[left[i][0]] += j   # j right elements smaller, came after
                merged.append(left[i]); i += 1
            else:
                merged.append(right[j]); j += 1
        while i < len(left):
            result[left[i][0]] += j       # all of right was smaller
            merged.append(left[i]); i += 1
        return merged + right[j:]

    merge_sort(indexed)
    return result

Variant 2 — Reverse Pairs (LC 493)

"Count pairs (i, j) where i < j and nums[i] > 2·nums[j]." The predicate is now left[i] > 2·right[j] instead of left[i] > right[j]. The critical detail: you must count before merging, not during, because the counting predicate (> 2×) and the merge predicate (>) are different — if you try to count during the merge you conflate the two conditions. Count first with a two-pointer scan across both sorted halves, then do the standard merge.

def reversePairs(nums):
    count = [0]

    def merge_sort(arr):
        if len(arr) <= 1:
            return arr
        mid = len(arr) // 2
        left  = merge_sort(arr[:mid])
        right = merge_sort(arr[mid:])

        # 1. COUNT cross-pairs satisfying the condition (before merging)
        #    left and right are both sorted — two-pointer over them
        j = 0
        for l in left:
            while j < len(right) and l > 2 * right[j]:
                j += 1
            count[0] += j     # first j right elements satisfy l > 2*right[j]

        # 2. MERGE normally (sorting for the next level up)
        merged = []; i = k = 0
        while i < len(left) and k < len(right):
            if left[i] <= right[k]:
                merged.append(left[i]); i += 1
            else:
                merged.append(right[k]); k += 1
        return merged + left[i:] + right[k:]

    merge_sort(nums)
    return count[0]

Variant 3 — Count of Range Sum (LC 327)

"Count subarrays whose sum lies in [lower, upper]." Convert to prefix sums: a subarray sum nums[i..j] = prefix[j+1] − prefix[i], so we want pairs (i, j) with i < j and lower ≤ prefix[j] − prefix[i] ≤ upper, i.e. prefix[j] − upper ≤ prefix[i] ≤ prefix[j] − lower. Now that's a cross-pair count on the prefix-sum array — count before merging with a two-pointer sweep (j advances as prefix[i] grows), then merge normally. Same skeleton, new predicate.

def countRangeSum(nums, lower, upper):
    from itertools import accumulate
    prefix = [0] + list(accumulate(nums))
    count = [0]

    def merge_sort(arr):
        if len(arr) <= 1:
            return arr
        mid = len(arr) // 2
        left  = merge_sort(arr[:mid])
        right = merge_sort(arr[mid:])

        # COUNT: for each right[j], count left[i] in [right[j]-upper, right[j]-lower]
        lo = hi = 0
        for r in right:
            while lo < len(left) and left[lo] <  r - upper: lo += 1
            while hi < len(left) and left[hi] <= r - lower: hi += 1
            count[0] += hi - lo

        # MERGE normally
        merged = []; i = j = 0
        while i < len(left) and j < len(right):
            if left[i] <= right[j]:
                merged.append(left[i]); i += 1
            else:
                merged.append(right[j]); j += 1
        return merged + left[i:] + right[j:]

    merge_sort(prefix)
    return count[0]

The unified skeleton (copy and adapt)

Every problem in this family fills the same three slots:

def solve(arr):
    answer = [0]          # or a list for per-element answers

    def merge_sort(arr):
        if len(arr) <= 1: return arr
        mid = len(arr) // 2
        left  = merge_sort(arr[:mid])
        right = merge_sort(arr[mid:])

        # SLOT 1 — COUNT cross-pairs using sortedness of left and right.
        #   Option A (count DURING merge): when you place left[i], j right
        #     elements have already been placed — all of them < left[i]. Add j.
        #     Use this when count predicate == merge predicate (e.g. "smaller than").
        #   Option B (count BEFORE merge, two-pointer): when count predicate ≠
        #     merge predicate (e.g. "> 2×", "sum in range"), do a separate two-pointer
        #     sweep across sorted left and right first, then merge.

        # SLOT 2 — MERGE normally to restore sorted order for the level above.
        merged = []; i = j = 0
        while i < len(left) and j < len(right):
            if left[i] <= right[j]:
                merged.append(left[i]); i += 1
            else:
                merged.append(right[j]); j += 1
        return merged + left[i:] + right[j:]

        # SLOT 3 — if you need per-element answers, carry original indices
        #   through the merge by sorting (index, value) pairs and writing
        #   back to a result array keyed by index.

    merge_sort(arr)
    return answer[0]
# O(n log n) time, O(n) extra space for the merge buffers.

When to reach for merge-sort counting, and why

  • The problem asks you to count pairs (i, j) with i < j satisfying some cross-element relation, and n can be up to 10⁵. This is the primary signal. The brute O(n²) is too slow; you need O(n log n). The merge step is the only part of a comparison sort that ever compares an element from the "left portion" against an element from the "right portion" — which is exactly a cross-pair. If the relation you want to count is one that sortedness makes easy to sweep in linear time, merge sort gives you that sweep for free at every level.
  • The counting predicate is monotone in one argument when the other is fixed — e.g. "smaller than," "> 2×," "sum in [lower, upper]." Monotonicity is what lets you use a two-pointer or advance a pointer without backtracking. If the predicate requires arbitrary element interactions, the two-pointer sweep doesn't work and merge sort doesn't help.
  • Per-element answers ("for each i, how many j > i satisfy ...") not just a global count. Carry original indices through the merge as (index, value) pairs and write each element's count back to a result array. The sort reorders elements for efficiency; the index keeps the answer attributed correctly.
  • The problem is really about prefix sums with a range condition. "Count subarrays whose sum is in [lower, upper]" is always a cross-pair count on the prefix-sum array — convert first, then apply the merge-sort skeleton. Whenever a subarray-aggregate question resists direct DP or prefix-sum hashing, this is the next thing to try.
  • Segment tree / BIT (Lesson 41) is the alternative you should compare. Both solve the same class in O(n log n). Merge sort is often simpler to code and needs no coordinate compression. The value-indexed counting tree is more flexible when you need range-query results beyond counts. If you're stuck on which to use, merge sort is a safer default for pure counting on the original array; the tree wins when you need per-query answers or dynamic inserts.

A trap: when "count pairs" does NOT need merge sort

Trap

"Count pairs (i, j) with nums[i] + nums[j] == target" — this looks like a cross-pair count, but the relation is symmetric (order of i and j doesn't matter), there is no "left came before right in the array" constraint, and a hash map answers it in O(n): for each element, check how many earlier elements make the sum equal (Lesson 5). The merge-sort pattern is specifically for problems where the positional ordering matters — (i, j) with i < j — and the predicate compares their values in a monotone way. If the problem cares about positions but the predicate is just equality, hashing wins. If the problem cares about the ordering AND uses an inequality (smaller, larger, in a range), merge sort or a counting tree is the right tool.

Composition — a Hard built from merge-sort counting + earlier patterns

Count of Range Sum (LeetCode 327, Hard) — link. Composes this lesson's merge-sort cross-pair counting with prefix sums (Lesson 4) and the two-pointer advance on sorted halves (Lesson 2).

Show the decomposition (try it yourself first)

The problem: given nums and bounds [lower, upper], count the number of subarrays whose sum lies in [lower, upper].

Pattern A — prefix sums (Lesson 4): subarray sum nums[i..j] = prefix[j+1] − prefix[i]. So the condition becomes: count pairs (i, j) with i < j in the prefix array where lower ≤ prefix[j] − prefix[i] ≤ upper, i.e. prefix[j] − upper ≤ prefix[i] ≤ prefix[j] − lower. You have transformed a subarray problem into a cross-pair count on the prefix array. This transformation is always the first move for subarray-aggregate range problems.

Pattern B — merge-sort counting (this lesson): the cross-pair count respects position order (i < j) and the predicate on the values is a range condition — the exact shape that works with merge sort. At each merge step, left and right are both sorted. For each element right[j], the left elements satisfying the range condition form a contiguous window (because left is sorted), so two pointers lo and hi sweep it in O(1) amortised per right element.

Pattern C — two-pointer advance (Lesson 2): the two-pointer sweep inside the merge step works because the left array is sorted and the window for each right[j] only moves forward as right[j] increases — the classic monotone-advance that turns O(n²) into O(n) per level.

def countRangeSum(nums, lower, upper):
    from itertools import accumulate
    prefix = [0] + list(accumulate(nums))   # Pattern A: convert to prefix sums
    count = [0]

    def merge_sort(arr):
        if len(arr) <= 1: return arr
        mid = len(arr) // 2
        left  = merge_sort(arr[:mid])
        right = merge_sort(arr[mid:])

        # Pattern B+C: two-pointer count BEFORE merging
        lo = hi = 0
        for r in right:                         # for each right[j]
            while lo < len(left) and left[lo] <  r - upper: lo += 1   # lo: lower bound
            while hi < len(left) and left[hi] <= r - lower: hi += 1   # hi: upper bound
            count[0] += hi - lo                 # left[lo..hi-1] all satisfy the condition

        # Standard merge to sort for the level above
        merged = []; i = j = 0
        while i < len(left) and j < len(right):
            if left[i] <= right[j]:
                merged.append(left[i]); i += 1
            else:
                merged.append(right[j]); j += 1
        return merged + left[i:] + right[j:]

    merge_sort(prefix)
    return count[0]

The Hard = (prefix sum to reframe subarray condition as a cross-pair condition) + (merge sort to get sorted halves "for free") + (two-pointer sweep of the sorted left window for each right element). Peel off the range condition and it is inversion count; add the range and you need the window sweep — exactly how composed hards tend to layer one more requirement on top of a simpler core.

Reference card — Merge Sort as a Counting Tool

When, and why

Use it when you need to count pairs (i, j) with i < j satisfying a monotone cross-element predicate (smaller than, greater than 2×, sum in range) and n is up to 10⁵ so O(n²) is too slow. The merge step naturally compares every left-half element against every right-half element in O(n) total; by recording these comparisons instead of discarding them, you get O(n log n) counting. The key requirement: the counting predicate must be monotone so a pointer or two-pointer sweep can replace a linear scan, keeping each merge level at O(n).

The two counting modes

Count during the merge when the count predicate equals the merge predicate (e.g. "count left[i] > right[j]"): when you place left[i], j right elements have already been moved out, all smaller — add j. Count before the merge when the predicates differ (e.g. "left[i] > 2·right[j]" or "right[j] − left[i] in [lower, upper]"): do a separate two-pointer sweep over the sorted halves, then merge normally. Never conflate the two — mixing count and merge logic when the predicates differ gives wrong answers.

Skeleton

def merge_sort(arr):        # returns sorted arr; side-effects the answer
    if len(arr) <= 1: return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid]); right = merge_sort(arr[mid:])
    # --- COUNT (before or during merge) ---
    # --- MERGE normally ---
    merged = []; i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]: merged.append(left[i]); i += 1
        else:                    merged.append(right[j]); j += 1
    return merged + left[i:] + right[j:]
# O(n log n). Carry (orig_index, val) pairs for per-element answers.

Classic problems

Count Inversions (global count, count-during), Count of Smaller Numbers After Self (315, Hard — per-element count, carry indices), Reverse Pairs (493, Hard — 2× twist, count-before), Count of Range Sum (327, Hard — prefix-sum + range window), The Skyline Problem (218, Hard — divide-and-conquer merge of partial answers).

Compare with Segment Tree / BIT (Lesson 41)

Both approaches solve the same counting problems in O(n log n). Merge sort: no coordinate compression needed, simpler to code from scratch, naturally handles the positional-order constraint. Value-indexed tree (Lesson 41): more flexible when you need per-query answers on an online stream, or when the domain is coordinate-compressed. When in doubt, try merge sort first — if the predicate is a clean inequality or range, it will work.
