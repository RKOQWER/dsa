DP Recognition — the recipe that turns exponential recursion into a table

Dynamic programming is the single biggest interview filter, and it is where most people freeze. The cure is to stop thinking of DP as a bag of tricks and start treating it as one mechanical recipe: find the choice, write the recurrence, notice the repeats, cache them. By the end of this lesson you will be able to look at a problem and derive whether DP applies — not recall whether you've seen it.

Deriving DP from a brute-force recursion

Take the cleanest possible case: Fibonacci. fib(n) = fib(n-1) + fib(n-2). Write the obvious recursion and watch what goes wrong.

Derive it

Brute force:

def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)

Spot the waste: draw the call tree for fib(5). fib(3) is computed twice, fib(2) three times, fib(1) five times. The tree has roughly 2ⁿ nodes, but there are only n distinct subproblems: fib(0)…fib(n). We are re-solving the same handful of subproblems an exponential number of times. That gap — few distinct subproblems, re-solved endlessly — is the entire signal for DP.

The insight (= the pattern): cache each subproblem's answer the first time you compute it, and return the cache on every later call. The call tree collapses to n unique computations.

from functools import cache
@cache
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)   # now O(n)

That's it. DP is nothing more than recursion plus a memory of answers you've already computed. Every DP you will ever write is this move applied to a harder recurrence.

The two conditions, stated so you can test for them

A problem is DP exactly when both of these hold, and you can check them from the problem statement:

  • Optimal substructure. The answer to the whole problem can be built from answers to strictly smaller versions of the same problem. Concretely: you can describe a choice at the current step such that, after making it, what remains is a smaller instance of the identical problem. If you cannot phrase "make one choice, then I face a smaller version of the same problem," it is not DP.
  • Overlapping subproblems. Those smaller versions are reached again and again through different choice sequences. This is what makes caching pay off — if every subproblem were distinct, caching would save nothing and plain recursion or greedy would do.

The recipe — the same five steps for every DP

Once you suspect DP, you never improvise. You run these five steps, in order, every time. They are written as actions you perform, not facts to memorize.

  1. Name the state. Decide what parameters fully describe a subproblem — the smallest set of values such that two calls with the same values must have the same answer. For Fibonacci it is just n. For a walk through an array it is usually "an index i, meaning the subproblem on the suffix starting at i." Getting the state right is 80% of the work; everything else follows.
  2. Write the recurrence by enumerating the choice. At the current state, list every move you could make. Each move consumes part of the problem and leaves a smaller state. The recurrence combines the results of those smaller states — a max/min for optimization, a + for counting, an or for feasibility.
  3. State the base cases. The smallest states whose answers are known without recursing — usually an empty suffix, index past the end, or n < 2.
  4. Memoize (top-down). Wrap the recursion in a cache keyed by the state. This is already a correct, efficient DP; many interviews accept it as the final answer.
  5. Optionally convert to tabulation (bottom-up). Fill a table in an order where every state's dependencies are computed before it. This removes recursion overhead and often lets you shrink memory to O(1) by keeping only the last row/few values.

Memoization vs. tabulation — which, and why

These are two implementations of the identical recurrence, so pick by convenience, not correctness. Top-down memoization is easier to write because it follows the recurrence literally and only computes states you actually reach, which matters when the state space is large but sparsely used. Bottom-up tabulation is worth the extra thought when you want to drop the recursion stack (deep states can overflow it) or when you can see that each state only depends on the previous row, which lets you throw the rest of the table away and run in O(1) extra space.

from functools import cache

def solve(problem):
    @cache
    def dp(state):
        if is_base(state):
            return base_value(state)

Composition — a Hard built from DP + an earlier pattern

Russian Doll Envelopes (Hard) — link. This composes DP (Longest Increasing Subsequence) with sorting as a tool (Lesson 11) and binary search (Lesson 10).

Show the decomposition (try it yourself first)

The problem: an envelope fits in another only if both width and height are strictly larger. Find the longest chain of nesting envelopes. Two dimensions must both increase.

Pattern A — sorting as a tool (Lesson 11): sort by width ascending. Now one dimension is handled: any valid chain reads left-to-right in this order. But ties in width are a trap — two equal widths can't nest, so for equal widths sort height descending, which prevents the algorithm from ever picking two same-width envelopes in the same increasing run.

Pattern B — reduce to a known 1-D problem: after sorting, the answer is the Longest Increasing Subsequence of the heights alone. The width constraint is already enforced by the sort order, so a classic LIS on heights solves it.

Pattern C — binary search (Lesson 10) to make LIS fast: the O(n²) DP for LIS is too slow here; the O(n log n) LIS keeps a "tails" array and uses binary search to place each height. That is DP's recurrence accelerated by binary search over the tails.

The Hard = (sort to kill one dimension) + (LIS recurrence) + (binary search to speed LIS). Each piece you already own. Naming the three pieces is the whole battle.

Reference card — DP Recognition

When it is DP, and why

  • Optimal substructure: you can phrase "make one choice now, then face a smaller version of the same problem." The whole answer is built from answers to smaller identical problems.
  • Overlapping subproblems: those smaller problems recur through different choice paths, so caching each one turns exponential work into polynomial. If subproblems never repeat, it is not DP (it is greedy, divide-and-conquer, or plain recursion).

The recipe (same every time)

  1. Name the state — the minimal parameters that identify a subproblem.
  2. Write the recurrence by enumerating the choice at the current state.
  3. State base cases.
  4. Memoize top-down (cache keyed by state).
  5. Optionally tabulate bottom-up and shrink memory.

How to combine sub-answers

Use max or min for "best value" problems, + for "count the ways" problems, and or for "is it possible" problems. The combine operator is dictated by what the question asks for.

Template

from functools import cache
@cache
def dp(state):
    if base(state): return base_value
    return combine(value(c) + dp(next(state, c)) for c in choices(state))
