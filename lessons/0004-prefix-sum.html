Prefix Sum & Difference Arrays — derived from repeated re-summing

Deriving prefix sums from scratch

Take the cleanest case. You're given an array and must answer many queries of the form "what is the sum of a[i..j]?"

Derive it

Brute force: for each query, loop from i to j and add. One query is O(n); with q queries it's O(n·q), which is brutal when both are large.

Spot the waste: two overlapping queries — say a[0..5] and a[0..7] — recompute almost the same sum. The second only needs a[6] + a[7] more than the first, yet brute force re-adds all eight. Every query redundantly re-adds a prefix that other queries already covered. The repeated work is the summing of shared prefixes.

The insight (= the pattern): precompute one array P where P[k] is the sum of the first k elements (P[0] = 0). Then the sum of a[i..j] is simply P[j+1] − P[i] — the whole-to-j sum minus the whole-to-just-before-i sum. Building P is one O(n) pass, and every query afterward is O(1) subtraction. You traded re-summing per query for subtracting two precomputed totals.

The deeper principle (so it transfers)

A prefix array turns a range question into the difference of two point lookups. That is the whole idea, and it generalizes: a prefix of sums answers range-sum queries; a prefix of XORs answers range-XOR queries; a 2D prefix answers rectangle-sum queries. The complementary trick, the difference array, runs the idea backwards — when you must apply many range updates (add a value to every element of a[i..j]) and only read the array at the end, you record +v at index i and −v at index j+1, then take a prefix sum once to realize all updates in O(n) total instead of O(n) per update.

When to use it, and the flavors

Prefix sums for range queries

You reach for a prefix sum when the problem fires many range-aggregate questions at a static array — repeated "sum of this subarray" or "sum of this rectangle" — and the array itself does not change between queries. You spend one linear pass building the prefix totals, after which each query is a constant-time subtraction. It works because a range aggregate is exactly the difference between two cumulative totals, so once the totals are stored, no scanning is ever needed again.

Prefix sum plus a hashmap — derive it by fixing bottlenecks

Use this combination when you must count contiguous subarrays with a target sum k (or a sum divisible by k), especially when numbers may be negative. Negatives rule out a sliding window: its running sum is no longer monotonic, so moving a pointer does not reliably move you toward the target. You do not need to memorize a trick; follow the waste until the right tool becomes inevitable.

Derive it

1. Try the obvious way. Pick every start i and end j, then add the elements from i through j. This repeatedly walks the same stretch of array, costing O(n3) in the most direct version. Even if you improve the inner sum bookkeeping, checking every pair of endpoints is still O(n2). The bottleneck is re-adding the same elements.

2. Stop re-counting with prefix sums. Let P[t] be the sum of everything before index t, with P[0] = 0. Then the sum from i through j is P[j + 1] − P[i]: the total at the end minus the total just before the start. You can now update a running prefix total in one pass instead of re-adding a subarray. But at each current prefix, scanning all older prefixes to find a match still costs O(n2) overall.

3. Reframe the search with algebra. At the current endpoint, let the running total be P[current]. A subarray ending here sums to k exactly when P[current] − P[old] = k. Isolate the unknown history value: P[old] = P[current] − k. You are no longer checking every old prefix for some vague relationship; you are hunting one exact number. If the current total is 15 and k is 7, the only prefix you need is 8.

4. Use the tool for exact history lookup. A hashmap records how many times each earlier prefix sum occurred. At each position, look up running − k and add that frequency to the answer, because every matching old prefix starts one valid subarray. Then record the current running total for later positions. Seed the map with {0: 1} so a prefix that itself equals k is counted. Lookup and update are O(1) on average, making the full scan O(n).

The chain to remember: do not re-add sections → use prefix sums; do not scan backward through old prefix sums → rearrange the equation to find the one value needed; need to find that exact value immediately → store prefix frequencies in a hashmap. The hashmap stores counts, not just presence, because the same old prefix can occur several times and each occurrence creates a different valid subarray.

Difference array for range updates

You reach for a difference array when you must apply a batch of "add v to every element in range [i, j]" operations and only need to read the final array afterward. Instead of touching every element of each range, you mark the start and one-past-the-end of each update, then sweep once. It works because adding to a contiguous range affects the differences between neighbors at only two points — the entry and the exit — so recording those two edits and integrating once reproduces every update.

The template (reproduce from memory)

# 1D prefix sum: range-sum queries in O(1) after O(n) build
def build_prefix(a):
    P = [0] * (len(a) + 1)
    for i, x in enumerate(a):
        P[i + 1] = P[i] + x
    return P
# sum of a[i..j] inclusive:
#   P[j + 1] - P[i]

# Count subarrays summing to k (handles negatives) via prefix + hashmap
from collections import defaultdict
def subarrays_sum_k(a, k):
    seen = defaultdict(int)
    seen[0] = 1                  # empty prefix
    run = 0
    count = 0
    for x in a:
        run += x
        count += seen[run - k]   # a prefix equal to run-k closes a subarray = k
        seen[run] += 1
    return count

# Difference array: apply range adds, then integrate once
def range_adds(n, updates):      # updates: list of (i, j, v)
    diff = [0] * (n + 1)
    for i, j, v in updates:
        diff[i] += v
        diff[j + 1] -= v
    out = [0] * n
    run = 0
    for idx in range(n):
        run += diff[idx]
        out[idx] = run
    return out

Composition — how a Hard is built from this pattern

Subarray Sum Equals K (Medium) escalates to the Count of Range Sum (Hard) — link. The Hard composes the prefix-sum reformulation (this lesson) with the two-pointer / merge-counting idea (Lesson 2's converging-pointer logic over a sorted order).

Show the decomposition (try it yourself first)

The ask: count subarrays whose sum lies in [lower, upper]. First reformulate with prefix sums: a subarray a[i..j] has sum in range exactly when P[j+1] − P[i] is in [lower, upper], i.e. for each right endpoint P[j+1] you need the count of earlier prefixes P[i] lying in [P[j+1] − upper, P[j+1] − lower].

Piece A — prefix sums: turn "sum of a subarray in range" into "count earlier prefix values inside a shifted range." Pure Lesson 4.

Piece B — counting over a sorted order: counting how many earlier prefixes fall in a numeric window is done during a merge sort of the prefix array. While merging two sorted halves, for each left-half prefix you advance two pointers over the right half to count values inside [lower', upper'] — the same two-pointer convergence idea from Lesson 2, now used to count rather than to find a pair. Each level of the merge is linear, giving O(n log n).

The Hard = (prefix-sum reformulation) + (two-pointer counting inside a merge sort). Name the two halves and the intimidating part dissolves.

Reference card — Prefix Sum & Difference Array

When to use it, and why

  • Prefix sums for range queries. Many "sum of this subarray/rectangle" questions on a static array. Build cumulative totals once; each query is the difference of two totals in O(1), because a range aggregate is exactly that difference.
  • Prefix + hashmap for counting subarrays. "How many subarrays sum to k / are divisible by k", especially with negative numbers (which break sliding windows). Store counts of each running prefix; a subarray equal to k ending now exists wherever a prefix equal to run − k appeared before — a lookup, not a scan.
  • Difference array for range updates. Many "add v to range [i, j]" updates, read only at the end. Record +v at i and −v at j+1, then prefix-sum once, because a range add only changes neighbor differences at the two edges.

The one-line reason it works

A prefix array converts a range question into the difference of two point values; a difference array runs that in reverse so many range updates collapse into two point edits each.

Discrimination test

Prefix sums assume the array is static between queries; if elements are updated between queries you need a Fenwick/segment tree instead. The prefix+hashmap counting trick is specifically what you reach for when sliding window fails due to negative numbers.

Templates (Python)

# range sum
P[0] = 0; P[k+1] = P[k] + a[k]
# sum a[i..j] = P[j+1] - P[i]

# count subarrays == k (negatives ok)
seen = {0: 1}; run = 0; count = 0
for x in a:
    run += x
    count += seen.get(run - k, 0)
    seen[run] = seen.get(run, 0) + 1

Complexity and classic problems

Build O(n), query O(1); 2D build O(mn), query O(1). Classic set: Range Sum Query - Immutable (Easy), Subarray Sum Equals K (Medium), Product of Array Except Self (Medium), Corporate Flight Bookings (Medium, difference array), Count of Range Sum (Hard).
