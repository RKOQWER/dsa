Tree BFS — deriving level-order and why "snapshot the queue size" is the whole trick

Some tree problems care about depth levels, not subtree structure: the right-side view, the level with the largest sum, zig-zag order, the minimum depth to a leaf. DFS fights these; BFS answers them directly. By the end you'll derive level-order traversal from scratch and know the one line — snapshotting the queue length — that separates "visit all nodes" from "process one level at a time".

Deriving level-order traversal from scratch

Take return the node values level by level, e.g. [[3], [9, 20], [15, 7]]. DFS naturally goes deep first, so it visits 3, then 9, then its children — it crosses levels, mixing them up. We need the opposite: finish a whole level before touching the next.

Derive it

The waste in DFS here: DFS's call stack explores one branch to the bottom before the next, so nodes at the same depth are visited far apart in time. To group by level, we'd have to tag every node with its depth and bucket afterward — awkward.

The insight: use a queue (first-in-first-out). If you enqueue the root, then repeatedly dequeue a node and enqueue its children, nodes come out in exactly non-decreasing depth order — a node's children are always enqueued after every node of the current level. That already gives a flat level-order visit. To get them grouped into levels, add one move: before processing, record how many nodes are in the queue right now — that count is exactly the current level's size. Process precisely that many, and everything you enqueue meanwhile belongs to the next level.

from collections import deque
def levelOrder(root):
    if not root: return []
    q, result = deque([root]), []
    while q:
        level_size = len(q)          # SNAPSHOT: size of THIS level
        level = []
        for _ in range(level_size):  # process exactly this level
            node = q.popleft()
            level.append(node.val)
            if node.left:  q.append(node.left)
            if node.right: q.append(node.right)
        result.append(level)
    return result

The single line level_size = len(q) taken before the inner loop is the entire trick. Without it you still visit every node, but you lose the level boundaries. With it, each inner loop handles one complete level. Every "per-level" tree problem is this skeleton with a different thing computed inside the inner loop.

When to reach for tree BFS, and why it works

Reach for BFS on a tree when the question is about levels or depth-order: group values by level, the average or max or sum of each level, the rightmost/leftmost node of each level (the side views), zig-zag order, the width of the tree, or the minimum depth to any leaf. The tell is any phrasing involving "level", "depth", "each row", "closest/shortest to the root", or a view from one side. It works because a FIFO queue releases nodes in non-decreasing depth order, and snapshotting the queue size at the start of each round carves that stream into exact level boundaries — one O(n) pass, each node enqueued and dequeued once.

Choose BFS over DFS specifically when distance from the root drives the answer. Minimum depth is the sharpest example: BFS finds the first leaf it reaches and can stop immediately, whereas DFS might plunge down a long branch before finding a shallow leaf elsewhere. Conversely, when the answer depends on subtree structure rather than level (heights, path sums, balance), DFS (Lesson 16) is the better fit. Many problems can be done either way; let the question's own words — "level/depth" vs "subtree/path" — pick for you.

Trap — computing the size inside the loop

The level size must be captured before the inner loop starts. If you write for _ in range(len(q)) and then append children inside that same evaluation, you're fine because range(len(q)) is evaluated once — but if you instead loop while len(q) > 0 and try to detect level ends by re-reading len(q), you'll merge levels, because the queue now holds a mix of this level and the next. Snapshot once, then drain exactly that many.

Composition — how a Hard is built from this pattern

Vertical Order Traversal of a Binary Tree (Hard 987) — link — composes BFS level-order (this lesson) with hashing / grouping by key (Lesson 5) and sorting with a custom comparator (Lesson 11). Try it before opening the decomposition.

Show the decomposition (try it yourself first)

Output nodes grouped by their column (left-to-right), and within a column sorted by row then by value. Columns are defined by assigning the root column 0, a left child column−1, a right child column+1.

Piece A (BFS level-order, this lesson): traverse the tree level by level, carrying each node's (row, col) alongside it in the queue. Processing in BFS order means that, within one column, nodes arrive in non-decreasing row order for free.

Piece B (hashing / grouping, Lesson 5): bucket every node into a hashmap keyed by its column: columns[col].append((row, val)). This is the exact "group items by a computed key" move from the hashing lesson.

Piece C (custom-comparator sort, Lesson 11): the tie-break rule — same column and same row, order by value — means each column's list must be sorted by (row, value), and the columns themselves emitted in increasing column index. That's a sort with a composite key, straight from the sorting lesson.

from collections import deque, defaultdict
def verticalTraversal(root):
    columns = defaultdict(list)          # hashing/grouping (Lesson 5)
    q = deque([(root, 0, 0)])            # (node, row, col) — BFS (this lesson)
    while q:
        node, r, c = q.popleft()
        if node:
            columns[c].append((r, node.val))
            q.append((node.left,  r + 1, c - 1))
            q.append((node.right, r + 1, c + 1))
    result = []
    for c in sorted(columns):            # columns left to right
        col_sorted = sorted(columns[c])  # custom (row, value) sort (Lesson 11)
        result.append([val for _, val in col_sorted])
    return result

The Hard = (BFS carrying coordinates) + (group-by-key hashing) + (composite-key sort). Three patterns you already own, stacked. Name the pieces and the Hard stops being hard.

Reference card — Tree BFS

The compressed version. A 2-minute re-read should reload the whole pattern.

When to use it, and why

Use on tree problems about levels or depth-order: group by level, per-level average/max/sum, side views, zig-zag, width, and minimum depth. It works because a FIFO queue releases nodes in non-decreasing depth order, and snapshotting the queue size each round splits that stream into exact levels — O(n), each node enqueued/dequeued once. Prefer BFS over DFS when distance from the root drives the answer (minimum depth can early-exit); prefer DFS when the answer depends on subtree structure.

The one trick

Take level_size = len(q) before the inner loop, then process exactly that many nodes. That single snapshot converts "visit all nodes" into "process one level at a time". Carry extra state (row/col, index) in the queue tuple when the problem needs it.

Template

from collections import deque
q = deque([root])
while q:
    size = len(q)                 # snapshot the level
    for _ in range(size):
        node = q.popleft()
        # ... compute for this node ...
        if node.left:  q.append(node.left)
        if node.right: q.append(node.right)

Trap

Snapshot the level size once; don't re-read len(q) mid-level, or this level and the next merge.
