Shortest Path — one idea, four tools chosen by the edge weights

"Fewest steps," "cheapest route," "minimum time to reach" — all shortest-path questions. The right tool is decided by two things: what the edge weights look like, and whether the graph can contain a cycle. This lesson derives why plain BFS already solves the unweighted case, why that breaks the moment edges have different costs, how Dijkstra fixes it by always expanding the closest-known node first, and why an acyclic graph (a DAG) lets you drop the heap entirely and even tolerate negative weights. The one case we leave out is a graph that has both cycles and negative edges — that needs Bellman-Ford.

Deriving the four tools from the edge weights

Derive it

Case 1 — every edge costs the same (unweighted). You already solved this in Lesson 21: BFS. Because the queue hands you nodes in order of increasing distance, the first time BFS reaches a node is via a fewest-edges path. Distance = number of edges, done. O(V + E).

Case 2 — edges have different non-negative costs. Now BFS breaks: reaching a node in fewer edges no longer means fewer total cost. A 1-edge path of weight 100 is worse than a 3-edge path of weight 6. The FIFO order is the wrong order.

Spot the waste / fix: what you actually want is to always process next the unfinalised node with the smallest known total distance. If you always expand the globally-closest frontier node, then at the moment you pop a node its shortest distance is settled — because every other route to it would have to go through a node that is at least as far, and (with non-negative weights) adding more edges can only increase cost. That ordering requirement is exactly what a min-priority-queue gives you.

The insight (= Dijkstra): keep a min-heap keyed by "best distance found so far." Pop the closest node, and for each neighbour, if going through this node is cheaper than its current best, update it and push the new distance. The heap guarantees you finalise nodes in increasing distance order — BFS's correctness argument, generalised from "edge count" to "total weight." O(E log V).

Case 3 — weights are only 0 or 1. You don't need a full heap. A 0-weight edge keeps you at the same distance, a 1-weight edge adds one. Use a deque: push 0-edges to the front and 1-edges to the back. This keeps the deque in nondecreasing distance order automatically — 0-1 BFS, O(V + E), no log factor.

Case 4 — the graph has no cycles (a DAG), and weights can be anything, even negative. The three tools above all discover a safe processing order as they run — but each leans on non-negative weights to do it, so none survives a negative edge. A DAG hands you a safe order for free: its topological order. Process the nodes in that order and relax each node's outgoing edges once. By the time you reach a node, every path into it has already been finalised (all its predecessors came earlier in topological order), so its distance is settled on first visit — no heap, no re-processing, and negative weights are fine because you never relied on "adding an edge can't lower the cost." Topological sort is O(V + E) and one relaxation sweep is O(V + E), so the whole thing is O(V + E). This is also how you get longest path in a DAG (NP-hard in a general graph): negate the weights, or relax for the maximum instead of the minimum.

What a priority queue (min-heap) is, in one paragraph

A min-heap is a container that always lets you remove the smallest item quickly. Python's heapq gives it to you on a plain list: heappush(h, (dist, node)) inserts, and heappop(h) removes and returns the pair with the smallest dist — each in O(log n). You don't need to have studied heaps as a topic yet; just treat it as "a pile that always hands back the cheapest thing." That single capability is the whole engine of Dijkstra.

The deeper principle (so it transfers)

All three tools are the same traversal with the same correctness idea — finalise nodes in order of increasing distance — and they differ only in the structure that enforces that order. When every step costs the same, a plain queue already enforces it (BFS). When steps cost 0 or 1, a double-ended queue enforces it (0-1 BFS). When steps have arbitrary non-negative costs, a min-priority-queue enforces it (Dijkstra). So the recognition move is: look at the edge weights, and pick the cheapest structure that still processes nodes closest-first. A grid where each move costs one is unweighted — reach for BFS, not Dijkstra; using a heap there is correct but needlessly slow.

The DAG case is the same idea seen from the other side. The first three tools discover a safe processing order while they run, and they can only do that because non-negative weights guarantee "closest-first" is also "finalise-able-first" — which is exactly why a single negative edge breaks all three. A DAG lets you precompute the safe order once, with topological sort, instead of discovering it. Because the order no longer depends on the weights, the weights are free to be negative. So the full recognition move is: if the graph is acyclic, relax in topological order and stop worrying about weight signs; otherwise look at the weights and pick BFS / 0-1 BFS / Dijkstra. (For a graph that has cycles and negative edges, neither family applies — that is Bellman-Ford's job, beyond this lesson.)

When to use which, and why

Use plain BFS when every move/edge has the same cost

If the problem counts steps, moves, or levels and each one is equal (a maze where each step is one, a word ladder where each edit is one), the number of edges is the distance, so BFS's level-by-level order already yields the shortest path with no weights to track. This is the common grid case and the cheapest option — don't reach for a heap.

Use Dijkstra when edges have different non-negative costs

When moving between nodes has varying positive cost (travel time, price, effort, risk) and you want the minimum total to reach a target, you need to always expand the closest-so-far node, which requires the min-priority-queue. Dijkstra is the default for "cheapest route with non-negative weights." It does not work with negative edges, because the assumption "adding edges can't decrease cost" fails.

Use 0-1 BFS when every edge weight is 0 or 1

Some grid problems let you take certain moves for free (weight 0) and others at cost 1 (for example, you may change direction for free but pay to break a wall). A full heap is overkill; a deque that front-loads the 0-cost moves keeps distances ordered and runs in linear time. Recognise it by "two kinds of moves, one free and one costing one."

Use DAG relaxation when the graph is acyclic

If the dependency structure has no cycles — task/course prerequisites, a build pipeline, states that only move forward in time, or a grid where moves are forced in one direction (e.g. strictly increasing values) — topologically sort the nodes and relax each one's edges in that order. It is O(V + E), beats Dijkstra's log factor, and is the only tool here that stays correct with negative edge weights. It is also the go-to for the longest path in a DAG (just relax for the max). Recognise it by "the graph can't loop back on itself."

The template (reproduce from memory)

from collections import deque
import heapq

# Unweighted shortest path: BFS
def bfs_dist(start, adj, n):
    dist = [float('inf')] * n
    dist[start] = 0
    q = deque([start])
    while q:
        u = q.popleft()
        for v in adj[u]:                 # each edge costs 1
            if dist[u] + 1 < dist[v]:
                dist[v] = dist[u] + 1
                q.append(v)
    return dist

# Non-negative weights: Dijkstra with a min-heap
def dijkstra(start, adj, n):             # adj[u] = list of (v, weight)
    dist = [float('inf')] * n
    dist[start] = 0
    pq = [(0, start)]                    # (distance so far, node)
    while pq:
        d, u = heapq.heappop(pq)         # always the closest unfinalised node
        if d > dist[u]:
            continue                     # stale entry, skip
        for v, w in adj[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                heapq.heappush(pq, (dist[v], v))
    return dist

# Weights are 0 or 1: 0-1 BFS with a deque
def zero_one_bfs(start, adj, n):         # adj[u] = list of (v, weight in {0,1})
    dist = [float('inf')] * n
    dist[start] = 0
    dq = deque([start])
    while dq:
        u = dq.popleft()
        for v, w in adj[u]:
            if dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                dq.appendleft(v) if w == 0 else dq.append(v)
    return dist

# Graph is a DAG, weights arbitrary (may be negative): relax in topological order
def dag_shortest_path(start, adj, n):    # adj[u] = list of (v, weight)
    indeg = [0] * n
    for u in range(n):
        for v, _ in adj[u]:
            indeg[v] += 1
    topo, q = [], deque(u for u in range(n) if indeg[u] == 0)
    while q:                             # Kahn's: produce a topological order
        u = q.popleft()
        topo.append(u)
        for v, _ in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)
    dist = [float('inf')] * n
    dist[start] = 0
    for u in topo:                       # every predecessor of u is already final
        if dist[u] == float('inf'):
            continue                     # u not reachable from start
        for v, w in adj[u]:
            if dist[u] + w < dist[v]:    # use max(...) here for longest path
                dist[v] = dist[u] + w
    return dist

Composition — how a Hard is built from this pattern

Swim in Rising Water (Hard 778) composes a Dijkstra-style shortest-path frontier (this lesson) with graph modeling (Lesson 20); it also rhymes with the "minimize the maximum" idea from binary search on the answer (Lesson 10), giving you two valid routes.

Show the decomposition (try it yourself first)

The problem: on an n×n grid of elevations, water rises over time; at time t you can stand on any cell with elevation ≤ t. Find the earliest time you can travel from the top-left to the bottom-right (moving to 4-neighbours).

Piece 1 — graph modeling (Lesson 20): cells are nodes, 4-adjacency gives edges. But the "cost" of a path is not a sum — it's the maximum elevation you must cross along the path. You want the path whose maximum elevation is smallest.

Piece 2 — Dijkstra adapted (this lesson): Dijkstra's correctness only needs that extending a path can't make its cost smaller. "Running maximum" satisfies that (adding a cell can only keep or raise the max), so use the same closest-first machinery, but define a node's cost as max(current path max, cell elevation) instead of a sum. Pop the frontier cell with the smallest running-max; the first time you pop the destination, that running-max is the answer.

Alternate route (Lesson 10): binary-search the answer time t, and for each t run a plain BFS/DFS over cells with elevation ≤ t to test "is the destination reachable?" Feasibility is monotone in t, so binary search applies — a clean example of two taught patterns solving the same Hard.

import heapq
def swimInWater(grid):
    n = len(grid)
    pq = [(grid[0][0], 0, 0)]            # (running max elevation, r, c)
    seen = {(0, 0)}
    while pq:
        t, r, c = heapq.heappop(pq)      # Piece 2: smallest running-max first
        if (r, c) == (n-1, n-1):
            return t
        for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)):   # Piece 1: 4-neighbours
            nr, nc = r+dr, c+dc
            if 0 <= nr < n and 0 <= nc < n and (nr, nc) not in seen:
                seen.add((nr, nc))
                heapq.heappush(pq, (max(t, grid[nr][nc]), nr, nc))

The Hard = (model the grid as a graph) + (Dijkstra's closest-first frontier, with cost redefined as a running maximum) — or alternatively (binary search the answer) + (plain reachability BFS).

The compressed version.

The one decision: look at the edge weights

All four are the same traversal with the same correctness idea — finalise nodes in increasing distance order — differing only in how that order is obtained: the first three enforce it with a data structure as they run, the DAG case precomputes it with a topological sort.

  • All edges equal (unweighted) → BFS, O(V + E). The FIFO queue already visits in distance order, so first arrival is shortest. Default for grids where each move costs one.
  • Non-negative varying weights → Dijkstra, O(E log V). A min-priority-queue always pops the closest unfinalised node, so its distance is settled on pop. Fails with negative edges.
  • Weights are 0 or 1 → 0-1 BFS, O(V + E). A deque: push 0-edges to the front, 1-edges to the back, keeping distances ordered without a heap.
  • Graph is a DAG (any weights, incl. negative) → relax in topological order, O(V + E). Topological order is a safe processing order independent of the weights, so no heap is needed and negative edges are fine. Also gives longest path in a DAG (relax for the max).

Priority queue, briefly

A min-heap (Python heapq) always hands back the smallest item in O(log n): heappush(h,(dist,node)) / heappop(h). That "always return the cheapest" is the engine of Dijkstra.

Dijkstra template

dist = [inf]*n; dist[s] = 0; pq = [(0, s)]
while pq:
    d, u = heappop(pq)
    if d > dist[u]: continue           # skip stale
    for v, w in adj[u]:
        if d + w < dist[v]:
            dist[v] = d + w
            heappush(pq, (dist[v], v))

DAG template (relax in topological order)

order = topological_sort(adj, n)       # Kahn's or DFS post-order reversed
dist = [inf]*n; dist[s] = 0
for u in order:                        # predecessors of u already final
    if dist[u] == inf: continue
    for v, w in adj[u]:
        if dist[u] + w < dist[v]:      # max(...) for longest path in a DAG
            dist[v] = dist[u] + w
