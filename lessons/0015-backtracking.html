Backtracking — deriving the one template behind subsets, permutations, and N-Queens

Backtracking looks like many different tricks — subsets, permutations, combinations, Sudoku, word search. It is actually one template. By the end you'll derive that template from scratch and see how every "generate/enumerate all valid X" problem is the same do / recurse / undo loop with different choices and a different validity check.

Deriving the backtracking template from scratch

Take the cleanest case: generate all subsets of [1, 2, 3].

Derive it

Brute force thinking: there are 2ⁿ subsets, so any correct method is exponential — fine, that's inherent, not waste. The real question is how to systematically produce every subset exactly once without forgetting any.

The insight: reframe "pick a subset" as a sequence of independent yes/no decisions — for each element, include it or not. That turns the problem into walking a decision tree: at depth i you decide element i. Every root-to-leaf path is one subset. Now recursion (Lesson 14, the accumulate flavor) writes itself: at each element, try "include", recurse, then undo and try "exclude".

def subsets(nums):
    result, path = [], []
    def backtrack(i):
        if i == len(nums):          # base: decided every element
            result.append(list(path))
            return
        path.append(nums[i])        # DO: include nums[i]
        backtrack(i + 1)            # RECURSE on the rest
        path.pop()                  # UNDO: exclude it
        backtrack(i + 1)            # RECURSE on the rest without it
    backtrack(0)
    return result

The undo (path.pop()) is the heart of backtracking: it restores state so the next branch explores a clean slate. Without it, the "include" choice would leak into the "exclude" branch and poison every later subset. Everything else — permutations, N-Queens, Sudoku — is this same tree walk with different choices and a pruning check added.

The universal template

Once you see subsets as a decision tree, every backtracking problem fits this shape. Only three slots change between problems:

def backtrack(state, path, result):
    if is_a_complete_solution(state):     # SLOT 1: when is a path done?
        result.append(list(path))
        return
    for choice in candidates(state):      # SLOT 2: what are the choices here?
        if not is_valid(choice, path):    # SLOT 3: prune invalid branches early
            continue
        path.append(choice)               # do
        backtrack(advance(state, choice), path, result)   # recurse
        path.pop()                        # undo
  • Slot 1 — completion test: for subsets it's "decided all elements"; for permutations "path length == n"; for N-Queens "placed a queen in every row".
  • Slot 2 — candidate choices: for subsets it's include/exclude; for permutations it's "every unused number"; for N-Queens "every column in this row".
  • Slot 3 — pruning: the step that makes backtracking fast. The moment a partial path can't possibly extend to a valid solution, you continue and skip that entire branch. In N-Queens, if a column or diagonal is already attacked, you never even recurse into it — you prune a whole subtree.

When to reach for backtracking, and why it works

Reach for backtracking when the problem asks you to generate or count all valid configurations — all subsets, all permutations, all combinations summing to a target, all ways to place pieces on a board, all valid partitions of a string. The tell is the word "all" (or "how many ways") combined with building a solution out of a sequence of discrete choices, and a small input bound (often n ≤ 20) that signals an exponential search is intended. It works because it walks the full decision tree of choices, and the undo step guarantees each branch is explored against clean state, so no configuration is produced twice or skipped.

The reason it is not simply "brute force all 2ⁿ then filter" is pruning: by checking validity as you build, you discard impossible branches before exploring them, often cutting the real work far below the worst-case bound. It does not fit when you only need the best single answer under overlapping subproblems — that overlap means dynamic programming (Part 5) will be exponentially faster, because backtracking re-derives the same sub-configurations instead of caching them.

Trap — the copy and the duplicate-skip

Two silent bugs ambush beginners. First, result.append(path) instead of result.append(list(path)) stores a reference to the one list that keeps mutating — you end up with a result full of identical (usually empty) lists. Always store a copy. Second, when the input has duplicates and the problem wants unique results (Subsets II, Permutations II, Combination Sum II), you must sort first and skip a choice equal to its previous sibling at the same tree level — otherwise you generate the same configuration many times. Matching the dedup rule to the problem is the difference between accepted and "wrong answer".

Composition — how a Hard is built from this pattern

N-Queens (Hard 51) — link — composes the backtracking template (this lesson) with hashing / seen-sets (Lesson 5) for O(1) attack checks. Try it before opening the decomposition.

Show the decomposition (try it yourself first)

Place one queen per row (that alone forbids row conflicts). At row r you choose a column; the configuration is valid if no earlier queen shares the column or either diagonal.

Piece A (backtracking, this lesson): the decision tree is "for each row, try each column"; the do/recurse/undo rhythm places a queen, recurses to the next row, then removes it. Completion test: reached a queen in every row.

Piece B (hashing / seen-sets, Lesson 5): the pruning check must be O(1), or the search is hopeless. Keep three sets — used columns, used "r−c" diagonals, used "r+c" anti-diagonals. A column is safe iff none of the three sets contains its keys. That constant-time validity check is pure Lesson-5 seen-set thinking, and it's what prunes whole subtrees instantly.

def solveNQueens(n):
    cols, diag, anti = set(), set(), set()   # seen-sets (Lesson 5)
    board, result = [], []
    def backtrack(r):
        if r == n:
            result.append(["".join(row) for row in board]); return
        for c in range(n):
            if c in cols or (r-c) in diag or (r+c) in anti:  # O(1) prune
                continue
            cols.add(c); diag.add(r-c); anti.add(r+c)        # do
            board.append("." * c + "Q" + "." * (n-c-1))
            backtrack(r + 1)                                 # recurse
            board.pop()                                      # undo
            cols.discard(c); diag.discard(r-c); anti.discard(r+c)
    backtrack(0)
    return result

The Hard dissolves into: backtracking supplies the tree walk, and seen-sets supply the O(1) conflict test that makes the pruning cheap. Name the pieces and the Hard stops being hard.

When to use it, and why

Use when the problem asks for all (or the count of) valid configurations built from a sequence of discrete choices — subsets, permutations, combinations, board placements, string partitions — usually with a small bound (n ≤ ~20) signalling an exponential search is intended. It works by walking the full decision tree; the undo step keeps each branch's state clean so nothing is produced twice or missed, and the validity check prunes impossible branches before exploring them.

The universal template — three slots change

def backtrack(state, path, result):
    if is_complete(state):
        result.append(list(path)); return   # store a COPY
    for choice in candidates(state):
        if not is_valid(choice, path): continue   # prune
        path.append(choice)      # do
        backtrack(advance(state, choice), path, result)  # recurse
        path.pop()               # undo

Slot 1 = completion test. Slot 2 = candidate choices here. Slot 3 = pruning check (the speed-up).

Two traps

Store list(path), not path (reference bug). For unique results with duplicate inputs, sort first and skip a choice equal to its previous sibling at the same level.

Not this pattern when…

You only need the single best answer and subproblems overlap — that's dynamic programming (Part 5), which caches instead of re-deriving.
