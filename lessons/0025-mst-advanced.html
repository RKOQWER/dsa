Minimum Spanning Tree — the cheapest way to connect everything

When a problem asks for the minimum total cost to connect all nodes (wire every house, link every city), you want a minimum spanning tree: a cycle-free subset of edges that connects every node at least total weight. This lesson derives why a simple greedy — "take the cheapest edge that doesn't create a cycle" — is provably optimal, giving you Kruskal's and its twin Prim's. We also meet bridges/articulation points lightly, as the "which connection is critical?" idea.

Deriving the MST greedy from first principles

Derive it

The task: connect all V nodes using some of the weighted edges, with minimum total weight. The result must be connected and have no cycle (a cycle means one edge is wasteful) — so it's a tree with exactly V−1 edges.

Greedy attempt: sort edges from cheapest to most expensive and add them one by one, skipping any edge whose two endpoints are already connected (that edge would only create a cycle without connecting anything new). Stop when you've added V−1 edges.

Why is this optimal? (the cut argument): consider any point mid-process and any way of splitting the nodes into two sides with no chosen edge crossing. The cheapest edge that crosses that split must be in some minimum spanning tree — because if an MST didn't use it, you could swap it in for a more expensive crossing edge and get a lighter tree, contradiction. Adding edges cheapest-first and skipping cycles always adds exactly such a safe crossing edge, so greed never regrets. That's Kruskal's algorithm, and the cycle-skip test is precisely a Union-Find check (Lesson 24).

The twin view (Prim's): instead of sorting all edges, grow one tree outward from a start node: repeatedly add the cheapest edge that leaves the current tree to a node not yet in it. A min-priority-queue of boundary edges gives you that cheapest crossing edge each step — the same "cheapest crossing edge is safe" principle, applied to a single growing component instead of many.

The deeper principle (so it transfers)

MST problems announce themselves as "connect everything at minimum total cost." The choice between the two algorithms is practical, not conceptual: Kruskal's (sort edges + Union-Find) is simplest when the graph is given as an edge list and is sparse; Prim's (grow from a seed with a min-heap) is natural when the graph is dense or already in adjacency form. Both rest on one fact — the cheapest edge crossing any cut is safe to take — so if you can see the problem as "a cut I must bridge as cheaply as possible," you can rederive either. The related "critical connection" idea (bridges and articulation points) asks the opposite question: which single edge or node, if removed, disconnects the graph — found with a single DFS that tracks how far back each subtree can reach.

When to reach for MST (and the bridge idea), and why

Use an MST when you must connect all nodes at minimum total cost

Whenever the goal is to link every item together and minimise the sum of chosen connection costs (cables, roads, pipes, merging points by distance), you want a minimum spanning tree. The giveaway is "connect all" plus "minimum total" — not shortest path between two specific nodes, but cheapest overall connectivity.

Choose Kruskal's for edge lists, Prim's for dense/adjacency graphs

Kruskal's sorts all edges once (O(E log E)) and uses Union-Find to skip cycle-forming edges, which is clean when you already have an edge list and the graph is sparse. Prim's keeps a frontier of candidate edges in a min-heap and grows a single tree (O(E log V)), which avoids sorting everything and suits dense graphs or a ready adjacency list. They produce the same minimum weight.

Use the bridges / articulation-point DFS when the question is "what's critical?"

If a problem asks which connections are essential — an edge whose removal splits the network (a bridge), or a node whose removal does (an articulation point) — a single DFS that records each node's discovery time and the earliest-discovered node its subtree can reach answers it in O(V + E). This is the "critical connections in a network" shape.

The template (reproduce from memory)

import heapq

# Kruskal's MST — needs the DSU from Lesson 24
def kruskal(n, edges):                 # edges: list of (weight, u, v)
    edges.sort()                       # cheapest first
    dsu = DSU(n)
    total, used = 0, 0
    for w, u, v in edges:
        if dsu.union(u, v):            # union returns False if it would make a cycle
            total += w
            used += 1
            if used == n - 1:          # a tree has exactly n-1 edges
                break
    return total if used == n - 1 else None   # None = graph not connectable

# Prim's MST — grow from node 0 with a min-heap
def prim(n, adj):                      # adj[u] = list of (weight, v)
    visited = [False] * n
    pq = [(0, 0)]                      # (edge weight into node, node)
    total = 0
    taken = 0
    while pq and taken < n:
        w, u = heapq.heappop(pq)
        if visited[u]:
            continue                   # stale boundary edge
        visited[u] = True
        total += w
        taken += 1
        for ew, v in adj[u]:
            if not visited[v]:
                heapq.heappush(pq, (ew, v))
    return total if taken == n else None

Composition — how a Hard is built from this pattern

Find Critical and Pseudo-Critical Edges in MST (Hard 1489) composes MST / Kruskal's (this lesson) with Union-Find (Lesson 24) and sorting as a tool (Lesson 11).

Show the decomposition (try it yourself first)

The problem: classify each edge. An edge is critical if removing it increases the MST weight (every MST must use it); it is pseudo-critical if it appears in some MST but not all.

Piece 1 — baseline MST (this lesson + Lesson 11): sort edges by weight and run Kruskal's to get the minimum total weight W.

Piece 2 — Union-Find as a reusable tester (Lesson 24): to test if an edge is critical, run Kruskal's while forbidding that edge; if you can't connect the graph, or the resulting weight exceeds W, the edge is critical. To test pseudo-critical, force that edge in first (union its endpoints, add its weight) then run Kruskal's on the rest; if the total still equals W, it belongs to some MST.

Piece 3 — sorting once, reused (Lesson 11): you keep the sorted edge list and keep track of each edge's original index (since the answer wants original indices), rebuilding a fresh DSU for each test.

Why brute force beyond this is worse: trying all subsets of edges is exponential; the "forbid one / force one, re-Kruskal" tests are O(E) each over E edges → O(E²·α), which is fine for interview constraints.

Reference card — MST & Advanced

The compressed version.

When and why

Use a minimum spanning tree when the goal is "connect all nodes at minimum total weight" (not shortest path between two). Both algorithms rest on one fact: the cheapest edge crossing any cut is safe to include.

  • Kruskal's: sort edges cheapest-first; add an edge iff its endpoints aren't already connected (Union-Find cycle check); stop at V−1 edges. O(E log E). Best for sparse graphs / edge lists.
  • Prim's: grow one tree from a seed; repeatedly add the cheapest boundary edge via a min-heap. O(E log V). Best for dense / adjacency graphs.

Critical connections (lighter)

A bridge is an edge whose removal disconnects the graph; an articulation point is such a node. One DFS tracking discovery time and the earliest reachable ancestor of each subtree finds them in O(V + E). The "critical connections in a network" shape.

Template (Kruskal's core)

edges.sort()                      # (weight, u, v)
dsu = DSU(n); total = used = 0
for w, u, v in edges:
    if dsu.union(u, v):           # skips cycle-forming edges
        total += w; used += 1
        if used == n-1: break
