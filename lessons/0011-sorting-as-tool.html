Sorting as a Tool — the cheapest way to create structure

You know how to sort. What interviews test is knowing when a problem becomes easy the instant you sort it, and how to bend the sort with a custom comparator. Sorting is rarely the answer by itself — it's the O(n log n) move that creates the ordering some other pattern needs. By the end you'll recognize that setup move cold.

Deriving the idea — sorting as a precondition factory

Take a concrete problem: given meeting intervals, can one person attend all of them (no two overlap)? Brute force: compare every pair of intervals for overlap → O(n²). Where's the waste? Most of those pairs are obviously disjoint, and you keep re-checking far-apart intervals that could never clash.

Derive it

The insight: if you first sort the intervals by start time, then an interval can only overlap the one immediately before it. Why? Because everything earlier starts even sooner and, if it didn't already overlap, ended before this one began. So a single O(n) sweep comparing each interval to its predecessor finds any conflict. The O(n²) pair comparison collapses because the sort created an ordering that made all but one comparison unnecessary.

That is the whole mental model for this lesson: sorting doesn't solve the problem — it manufactures a structure (adjacency, monotonicity, grouping) that a cheap linear pass can then exploit. When you're staring at an O(n²) brute force, one of the first questions to ask is: "if this input were sorted by the right key, would far-apart elements stop mattering?" If yes, sort and sweep.

Bending the sort — custom comparators

The default order is numeric or lexicographic. Many problems need a different order, and choosing that order is the entire solution. The classic is "arrange numbers to form the largest possible concatenation": the right order isn't "bigger number first" — [9, 30] should become "930", but [3, 30] should become "330", not "303". The correct rule is: a comes before b if the string a+b is larger than b+a. You derive the comparator by asking "for just these two, which ordering wins?" and trusting that a consistent pairwise rule produces a correct global order.

from functools import cmp_to_key

def largestNumber(nums):
    strs = list(map(str, nums))
    # pairwise rule: whichever concatenation is bigger decides the order
    def compare(a, b):
        if a + b > b + a:   return -1   # a should come first
        if a + b < b + a:   return 1    # b should come first
        return 0
    strs.sort(key=cmp_to_key(compare))
    out = "".join(strs)
    return "0" if out[0] == "0" else out   # all-zeros edge case

When the order is a simple function of each element, use a key instead of a comparator — key is faster and cleaner because it computes one sort-value per element. Reach for a full comparator (cmp_to_key) only when the order depends on comparing two elements together, as above, where no single per-element key captures it.

When sorting is the setup for greedy

A huge family of greedy problems becomes correct only after sorting by the right key: schedule the most meetings by sorting on end time, assign cookies by sorting both children and cookies, minimize waiting time by sorting ascending. The pattern is: sort so that the locally-best choice at each step is also globally safe. You will usually be able to argue "if I always take the item with the smallest/earliest X, I never regret it" — and that argument tells you which key to sort on.

Trap — sharpen your discrimination

Maximum Gap (Medium) asks for the largest gap between consecutive values after sorting. The obvious move is sort then scan — correct, but O(n log n), and the problem secretly wants O(n). Here sorting is a trap: the intended solution is bucket/radix-style, using the pigeonhole principle to avoid a comparison sort entirely. Lesson: "sort then scan" is the right first idea, but when the constraints demand linear time, sorting is exactly what you must give up.

Composition — how a Hard is built from this pattern

Create Maximum Number (Hard) — link — composes a custom-order greedy "max subsequence" with the same pairwise concatenation comparison you used for Largest Number (this lesson), plus a two-pointer merge (Lesson 2).

Show the decomposition (try it yourself first)

Pick k digits total from two arrays, preserving each array's relative order, to form the largest number. It decomposes into three pieces you already own:

Piece 1 — pick the best i digits from one array (monotonic-stack-free greedy): to keep the largest i-length subsequence in order, scan left to right and greedily drop a smaller leading digit when a bigger one arrives and you still have room. This is the "keep it as large as possible, position by position" greedy — a local-choice argument exactly like the sorting-for-greedy reasoning above.

Piece 2 — merge two candidate subsequences into the largest interleaving (two-pointer merge): at each step take from whichever array is "lexicographically larger from here on", compared with the same a+b vs b+a style pairwise rule from Largest Number. This is a two-pointer merge (Lesson 2) driven by a custom comparison (this lesson).

Piece 3 — try every split: for each way to take i digits from array one and k−i from array two, build and merge, keep the best.

The Hard = (custom-order greedy subsequence) + (pairwise-concatenation comparison from Largest Number) + (two-pointer merge). Every piece came from a lesson you've done. Name the pieces and it's assembly, not invention.

Reference card — Sorting as a Tool

The compressed version. Re-reading this should reload the whole pattern.

When to use it, and why

  • As a precondition factory. When a brute force is O(n²) because far-apart elements keep getting compared, sort by the right key so that only adjacent elements matter, then do a single linear sweep. Overlapping intervals, closest pairs, and duplicate-grouping all work this way.
  • As the setup for greedy. Many greedy algorithms are only correct after sorting on a specific key (end time, ratio, height), chosen so the locally-best pick is always globally safe.
  • With a custom comparator. When the needed order isn't numeric/lexicographic, define the order by asking "between just these two, which comes first?" — e.g. a+b > b+a for largest-concatenation.

The one-line reason it works

Sorting spends O(n log n) once to create an ordering (adjacency, monotonicity, grouping) that lets a cheap O(n) pass replace an O(n²) all-pairs comparison.

How to derive it cold

Facing an O(n²) brute force, ask: "if the input were sorted by some key, would far-apart elements stop mattering, leaving only neighbours to compare?" If yes, sort on that key and sweep. For ordering problems, derive the comparator from the two-element case and trust a consistent pairwise rule to give a correct whole.

Discrimination test (when it does NOT apply)

If the problem needs strictly linear time (Maximum Gap), or if sorting would destroy information you must keep (original indices, as in the unsorted Two Sum), don't sort — reach for counting/radix or a hashmap instead. "Sort then scan" is a strong first idea, not a law.

Template (Python)

# key-based sort (order is a function of each element)
items.sort(key=lambda x: (x.end, x.start))

# comparator-based sort (order depends on comparing two elements)
from functools import cmp_to_key
def cmp(a, b):
    if a + b > b + a: return -1
    if a + b < b + a: return 1
    return 0
strs.sort(key=cmp_to_key(cmp))

# sort-then-sweep skeleton
items.sort(key=lambda x: x.start)
