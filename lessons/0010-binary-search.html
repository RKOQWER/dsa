Binary Search — and the interview unlock: searching the answer itself

Everyone knows binary search on a sorted array. The thing that actually separates interview passes from fails is realizing you can binary-search over something that isn't an array at all — the space of possible answers. By the end you'll derive both from one idea, and know the exact precondition that licenses it.

Deriving classic binary search from the waste

Find a target in a sorted array. Brute force: scan left to right, O(n). Where is the waste? You check a[0], then a[1]… but the array is sorted, so when you look at the middle element and it's larger than the target, every element to its right is also larger. A single comparison just proved an entire half is hopeless — and the linear scan threw that proof away.

Derive it

Look at the middle. One comparison splits the array into "the half that could contain the answer" and "the half that provably can't." Discard the dead half, repeat on the live half. Each step halves the search space → O(log n). That halving-by-proof IS binary search. It isn't about arrays; it's about any space where one probe lets you discard half.

That last sentence is the whole lesson. Binary search needs exactly one thing: a monotone predicate — a yes/no test that is False, False, …, False, then True, True, …, True, with a single flip point. Sortedness is just the most common way to get one. Hold that thought.

The template that kills off-by-one bugs

Most binary-search bugs come from ad-hoc mid ± 1 juggling. Avoid them by always framing the problem as "find the first index where a predicate becomes True." This single template answers almost every variant.

# Find the FIRST index in [lo, hi) where pred(i) is True.
# pred must be monotone: False...False True...True
def first_true(lo, hi, pred):
    while lo < hi:
        mid = (lo + hi) // 2
        if pred(mid):
            hi = mid          # mid might be the answer; keep it in range
        else:
            lo = mid + 1      # mid is dead; discard it
    return lo                 # first True index, or hi if none

# classic "search value v in sorted a" expressed through it:
def search(a, v):
    i = first_true(0, len(a), lambda m: a[m] >= v)
    return i if i < len(a) and a[i] == v else -1

The unlock — binary search on the answer

Here is the leap. If binary search only needs a monotone yes/no predicate, the thing you search doesn't have to be an array index. It can be a candidate answer. This is the single most valuable interview pattern in this part of the course, so let's derive it from a real problem rather than state it.

Worked derivation: Koko Eating Bananas

Koko eats bananas at speed k per hour, one pile at a time; with piles [3,6,7,11] and h hours, find the minimum k that finishes within h hours.

Derive it

Brute force: try k = 1, 2, 3, …, and for each compute the hours needed; return the first k that fits. Trying every speed up to max(piles) is O(max · n).

Spot the structure: ask the key question — if speed k is fast enough to finish in time, is k+1 also fast enough? Obviously yes; eating faster never takes more hours. So "does speed k finish within h hours?" is a monotone predicate: False for small k, then flips to True once and stays True. That is exactly the precondition binary search demands.

The insight (= the pattern): don't search an array — binary-search the value of k in the range [1, max(piles)] for the first k where the predicate is True. The brute force's linear scan over speeds collapses to O(n · log(max)).

import math
def minEatingSpeed(piles, h):
    def hours_at(k):
        return sum(math.ceil(p / k) for p in piles)
    # pred(k): can Koko finish within h hours at speed k?  (monotone True-ward)
    lo, hi = 1, max(piles)
    while lo < hi:
        k = (lo + hi) // 2
        if hours_at(k) <= h:
            hi = k
        else:
            lo = k + 1
    return lo

How to SPOT "binary search on the answer" cold

You are looking at this pattern whenever the problem asks for the smallest (or largest) value that still satisfies some condition, and that condition behaves monotonically in the value — meaning once it becomes satisfiable at some value, every value in the same direction stays satisfiable. The tells in the wording are phrases like "minimum capacity", "minimum speed", "minimize the largest …", "maximize the smallest …", or any "largest/smallest X such that it's still possible." When you see that shape, define a boolean feasibility function feasible(x), convince yourself it is monotone, pick the [lo, hi] bounds for x, and binary-search for the flip point. The hard part is never the binary search — it is writing feasible(x) and proving it is monotone.

Trap — sharpen your discrimination

Find Minimum in Rotated Sorted Array II (Hard) looks like plain binary search, but duplicates break the monotone split: when a[mid] == a[hi] you genuinely cannot tell which half holds the minimum, so you can only shrink hi by one — which degrades to O(n) in the worst case. Lesson: binary search needs the predicate to stay monotone. Duplicates can destroy monotonicity, and when they do, the halving guarantee quietly dies. Always check that your one probe really does kill half.

Composition — how a Hard is built from this pattern

Hards are patterns stacked. Split Array Largest Sum (Hard) — link — composes binary search on the answer (this lesson) with a greedy sweep that you can derive directly from prefix-style running sums (Lesson 4 territory).

Show the decomposition (try it yourself first)

Split nums into m contiguous parts to minimize the largest part-sum. The phrase "minimize the largest" is the binary-search-on-the-answer tell.

Pattern A (binary search on the answer): the answer is some value cap — the largest allowed part-sum. Ask "feasible(cap): can we split into ≤ m parts if no part may exceed cap?" If a given cap works, any larger cap also works → monotone. So binary-search cap in [max(nums), sum(nums)].

Pattern B (greedy running-sum sweep to implement feasible): walk the array accumulating a running sum; whenever adding the next element would exceed cap, cut a new part and reset the accumulator to that element. Count the parts. This greedy uses the fewest parts possible for that cap — the same running-prefix-sum idea from Lesson 4, used here as a feasibility check rather than a query.

def splitArray(nums, m):
    def feasible(cap):
        parts, cur = 1, 0
        for x in nums:
            if cur + x > cap:
                parts += 1
                cur = 0
            cur += x
        return parts <= m
    lo, hi = max(nums), sum(nums)
    while lo < hi:
        cap = (lo + hi) // 2
        if feasible(cap):
            hi = cap
        else:
            lo = cap + 1
    return lo

The Hard = (binary search on the answer value) + (greedy running-sum feasibility check). Neither piece is hard alone. Name the pieces and the Hard dissolves.

Reference card — Binary Search

The compressed version. Re-reading just this should reload the whole pattern.

When to use it, and why

  • Classic (search a value / boundary in a sorted array). Because the array is sorted, one look at the middle proves an entire half can't contain the answer, so you discard half per step → O(log n).
  • On the answer (find the smallest/largest value that still works). When the question asks for a minimal or maximal value and "does value x work?" is monotone (once True, stays True in one direction), you binary-search the value itself instead of an index. Use it whenever you read "minimum capacity/speed", "minimize the largest", "maximize the smallest", or "largest/smallest X that's still possible."

The one-line reason it works

Binary search needs exactly one thing — a monotone yes/no predicate with a single False→True flip point. One probe at the middle discards everything on the dead side of the flip, halving the space each step.

How to derive it cold

  • Classic: on a sorted array, a comparison at the middle proves one half is hopeless — discard it, repeat.
  • On the answer: if the problem wants the extreme feasible value, define feasible(x), prove it's monotone in x, pick [lo, hi] bounds, and search for the flip. The real work is writing and justifying feasible, never the search loop.

Discrimination test (when it does NOT apply)

If no monotone predicate exists — the yes/no answer flips back and forth as the value grows, or duplicates destroy the clean split (Find Minimum in Rotated Sorted Array II) — binary search's halving guarantee is gone. Confirm every probe really eliminates one whole side before you trust O(log n).

Template (Python)

# one template for everything: first index where a monotone pred is True
def first_true(lo, hi, pred):       # search space [lo, hi)
    while lo < hi:
        mid = (lo + hi) // 2
        if pred(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo
# value-search: set lo/hi to the answer range, pred = feasible(x)

Complexity and classic problems

Time O(log n) classic, or O(n · log(range)) when each feasibility check is O(n). Space O(1).
