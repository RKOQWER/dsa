BST Patterns — one property (inorder = sorted) that trivializes a dozen problems

A binary search tree is just a binary tree with one extra promise: left subtree < node < right subtree, everywhere. That one promise collapses many "hard" tree problems into easy ones. By the end you'll reflexively ask, on any BST problem, "can I use the ordering to avoid visiting the whole tree?" — and you'll know the single fact that answers most of them: an inorder traversal of a BST yields the values in sorted order.

Deriving the BST toolkit from one property

Take validate a binary search tree. The naive check — "is node.left.val < node.val < node.right.val at every node?" — is a classic wrong answer: it only checks parent-child pairs, missing violations deeper down (a far-right descendant of the left subtree can still be larger than the root).

Derive it

Two ways to fix it, both from the ordering promise:

Approach 1 — carry valid bounds down (top-down, Lesson 16). The BST property means every node must lie within an open interval determined by its ancestors. The root may be anything; going left tightens the upper bound to the parent's value; going right tightens the lower bound. A node is valid iff it sits inside its inherited (low, high) range. This is the top-down "pass context down" flavor from tree DFS.

def isValidBST(root):
    def ok(node, low, high):
        if not node: return True
        if not (low < node.val < high): return False
        return ok(node.left, low, node.val) and ok(node.right, node.val, high)
    return ok(root, float('-inf'), float('inf'))

Approach 2 — inorder must be strictly increasing. Here's the deeper unlock: an inorder traversal of any BST produces its values in sorted order. So the tree is a valid BST iff its inorder sequence is strictly increasing. You don't even need bounds — walk inorder, and verify each value exceeds the previous one.

def isValidBST(root):
    prev = float('-inf')
    def inorder(node):
        nonlocal prev
        if not node: return True
        if not inorder(node.left): return False   # left
        if node.val <= prev: return False          # node
        prev = node.val
        return inorder(node.right)                 # right
    return inorder(root)

The second approach generalizes to a whole family: kth smallest, the two swapped nodes in "recover BST", closest value, range sum — all are questions about a sorted sequence that you happen to be reading off a tree via inorder.

The two BST superpowers

  • Inorder = sorted. Any problem that would be trivial on a sorted array (kth smallest, median-ish, "is it sorted", find two out-of-place elements) becomes trivial on a BST by walking inorder. You often don't even materialize the array — you track just the previous value or a running count, so it's O(h) space, not O(n).
  • Each comparison discards a whole subtree. Because left < node < right, comparing your target to the current node tells you which single child could contain it — exactly like binary search (Lesson 10) choosing a half. Search, insert, delete, lowest-common-ancestor, floor/ceiling, and "closest value" all exploit this to run in O(h) instead of O(n).

When to reach for BST techniques, and why they work

The trigger is simply that the problem states the tree is a binary search tree (or asks you to build/validate one). The instant you see "BST", ask the two superpower questions: "does inorder-as-sorted answer this?" and "can I discard a subtree at each node by comparing to the target?". They work because the ordering invariant is a structural form of sortedness — inorder linearizes it into a sorted stream, and the per-node comparison is binary search embedded in the tree shape, so navigation costs O(h): O(log n) on a balanced tree, O(n) on a degenerate one.

Do not fall back to generic whole-tree DFS (Lesson 16) on a BST when ordering would let you touch only one path — that throws away the very property that makes it a BST. And remember the worst case: if the tree is unbalanced (effectively a linked list), O(h) degrades to O(n); self-balancing variants fix that but are rarely required in interviews. When a problem gives a plain binary tree with no ordering promise, none of this applies — use Lesson 16 or 17 instead.

Composition — how a Hard is built from this pattern

Recover Binary Search Tree (Medium 99) — link — composes the "inorder = sorted" property (this lesson) with the "find the out-of-order elements in a sorted sequence" idea and the return-one-track-another side-state trick from tree DFS (Lesson 16). It's Medium-labelled but the reasoning is hard; it's the cleanest demonstration of the inorder superpower. Try it before opening the decomposition.

Show the decomposition (try it yourself first)

Exactly two nodes of a valid BST were swapped; restore it without changing structure. The O(n)-space brute force: inorder into an array, find the two positions that break sortedness, swap their values back. The elegant O(h)-space version removes the array.

Piece A (inorder = sorted, this lesson): if you read the tree inorder, exactly the two swapped values break the "strictly increasing" rule. In a sorted sequence with two elements swapped, you see either one descending adjacent pair (if the two are adjacent) or two descending pairs (if not). The first offender is the larger of the first pair; the second offender is the smaller of the last pair.

Piece B (track state on the side, Lesson 16): rather than build the array, do an inorder walk carrying prev (the previously visited node) and capture first and second as side-state the moment you detect a descent — exactly the "return nothing, update a global on the side" rhythm from tree DFS.

def recoverTree(root):
    first = second = prev = None
    def inorder(node):
        nonlocal first, second, prev
        if not node: return
        inorder(node.left)
        if prev and prev.val > node.val:     # a descent in sorted order
            if not first: first = prev        # larger of first bad pair
            second = node                     # smaller of last bad pair
        prev = node
        inorder(node.right)
    inorder(root)
    first.val, second.val = second.val, first.val

The Hard = (inorder gives a sorted stream) + (detect the two break points) + (capture them as DFS side-state). All pieces you already own. Name the pieces and the Hard stops being hard.

When to use it, and why

Triggered the instant a problem says "binary search tree". Two superpowers: (1) an inorder traversal yields values in sorted order, so anything easy on a sorted array is easy on a BST via inorder, often in O(h) space by tracking only the previous value or a count; (2) comparing your target to a node discards one whole subtree, so search/insert/delete/LCA/closest run in O(h). They work because the left < node < right invariant is structural sortedness — inorder linearizes it, and the per-node comparison is binary search inside the tree.

The two reflex questions on any BST problem

  • Does reading the tree inorder (sorted) answer it? (kth smallest, validate, min diff, recover, range)
  • Can I discard a subtree at each node by comparing to a target? (search, insert, delete, LCA, closest, floor/ceiling)

Templates

# inorder as sorted stream (O(h) space, track prev)
prev = -inf
def inorder(node):
    if not node: return
    inorder(node.left)
    visit(node.val, prev); prev = node.val   # compare to previous
    inorder(node.right)

# navigate by comparison (search), O(h)
while node and node.val != target:
    node = node.left if target < node.val else node.right

Watch out

An unbalanced BST degrades O(h) to O(n). A plain binary tree with no ordering promise means none of this applies — use Lesson 16/17 instead.
