Deriving the recursion skeleton from scratch

Take a plain task: sum a nested list like [1, [2, 3], [4, [5]]]. An iterative loop stalls immediately — you don't know how deep the nesting goes, so you can't write a fixed number of for loops.

Derive it

The waste in trying to be iterative: you'd need one loop per nesting level, but the depth is unknown. Any fixed loop count is either too few (misses deep items) or hard-codes a limit. The structure is self-similar: a nested list is "numbers, plus more nested lists that are the same kind of thing."

The insight (= recursion): if a sub-piece is the same shape as the whole, let the function call itself on the sub-piece and trust it to return the right answer. You only have to handle one level, plus a base case where there's no deeper level.

def nested_sum(x):
    if isinstance(x, int):      # BASE CASE: smallest indivisible thing
        return x
    total = 0
    for item in x:              # ONE level of work
        total += nested_sum(item)   # TRUST the recursion for the rest
    return total

You never reasoned about depth. You handled one level and delegated the rest. That leap of faith — "assume the recursive call already works on the smaller input" — is the whole skill. Everything in Parts 3 and 5 is a variation of it.

The three parts every recursion must have

Whenever you write a recursive function, name these three things explicitly or you will get it wrong:

  • Base case. The smallest input where the answer is immediate and you stop recursing. Missing or wrong base cases cause infinite recursion or off-by-one errors. Write this first.
  • The work at this level. What you do with the current element before or after delegating. For nested-sum it's "add this number"; for a tree it's "look at this node".
  • The recursive leap of faith. You call the function on strictly smaller input and assume it returns the correct answer for that input. You do not trace it down manually — if the base case and the combine step are right, the whole thing is right by induction.

The decision that trips everyone: return a value up, or accumulate into a shared result?

This is the single most important fork in recursion, and it's worth stating carefully because getting it wrong produces code that looks right but gives empty or doubled answers.

Returning a value up (bottom-up combine)

Each call computes its own answer from the answers its children returned, then hands one value back to its parent. You use this when the final answer is a single aggregate that is naturally built by combining sub-answers — a sum, a max depth, a count, a boolean "does this subtree satisfy X". The flow of information is upward: leaves answer first, the root answers last. Nested-sum above is exactly this shape.

Accumulating into a shared result (top-down collect)

Instead of returning, each call appends to a result list (or mutates shared state) that lives outside the recursion, usually passing a "path so far" down as an argument. You use this when you must enumerate many things — all root-to-leaf paths, all subsets, all permutations — where there is no single value to combine, you just want every complete path recorded. The flow of information is downward: you build the path on the way down and record it when you hit the base case.

How to decide, in one question

Ask: "Is the answer ONE combined value, or MANY enumerated things?" One value (sum, depth, count, yes/no) → return it up and combine children's returns. Many things (all paths, all subsets, every arrangement) → accumulate into a shared list and record at the base case. Backtracking (Lesson 15) is always the accumulate flavor; most tree-property problems (Lesson 16) are the return-up flavor.

The two templates (reproduce from memory)

# RETURN-UP (bottom-up combine): the answer is one aggregate value
def solve(node):
    if is_base(node):               # base case
        return base_value
    left  = solve(node.child_a)     # trust the recursion
    right = solve(node.child_b)
    return combine(node, left, right)   # build MY answer from theirs

# ACCUMULATE (top-down collect): the answer is many enumerated things
def solve(state, path, result):
    if is_complete(state):          # base case: a full candidate
        result.append(list(path))   # record a COPY of the path
        return
    for choice in choices(state):
        path.append(choice)         # do
        solve(advance(state, choice), path, result)   # recurse
        path.pop()                  # undo  (the "backtrack")

Notice the do / recurse / undo rhythm in the accumulate template — append a choice, recurse with it in place, then remove it so the next choice starts clean. That undo is why the pattern is called backtracking, and you will reuse this exact three-line rhythm throughout Part 3. The list(path) copy matters: if you append path itself, every entry in result points at the same list that keeps mutating.

When to reach for recursion, and why it works

Reach for recursion when the problem has self-similar structure: the input can be broken into one or more pieces that are smaller instances of the same problem. A tree is the purest example — each child is itself a tree. Nested data, "generate all arrangements", divide-and-conquer sorts, and "try a choice then solve the rest" problems all have this shape. It works because of induction: if your base case is correct and your combine step correctly builds the answer for an input of size n from correct answers for size n−1 (or the children), then by induction every size is correct — you never have to trace the full call tree by hand.

It does not fit when the problem has no smaller self-similar sub-instance, or when the recursion would recompute the same sub-answer exponentially many times with no caching (that overlap is exactly the signal for dynamic programming, Part 5 — recursion plus memoization). Recognizing "my recursion recomputes the same input over and over" is the bridge from this lesson to DP.

Composition — how a Hard is built from this skeleton

Sort List (Medium 148) — link — is a clean composition: it stacks the recursion skeleton (this lesson) on top of linked-list manipulation (Lesson 8). Try it before opening the decomposition.

Show the decomposition (try it yourself first)

The brute force — copy to an array, sort, rebuild — is O(n log n) time but O(n) extra space and ignores the list structure. The problem wants you to sort the list itself.

Piece A (recursion skeleton, this lesson): a list is self-similar — split it into two halves, each half is itself a list to sort. Base case: zero or one node is already sorted. Recurse on each half, trust both come back sorted, then combine.

Piece B (linked-list manipulation, Lesson 8): two sub-skills from that lesson do the real work. Finding the middle to split uses the fast & slow pointer technique; combining two sorted halves is the merge with a dummy node technique you already drilled.

def sortList(head):
    if not head or not head.next:          # base case
        return head
    # split via fast/slow (Lesson 8)
    slow, fast = head, head.next
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    mid = slow.next
    slow.next = None
    left  = sortList(head)                 # trust it
    right = sortList(mid)                  # trust it
    return merge(left, right)              # merge with dummy node (Lesson 8)

The Hard-feeling part dissolves once you name the pieces: recursion gives the divide-and-conquer shape, and the linked-list lesson supplies "find middle" and "merge". Neither piece is hard alone — that is the whole method for hards: name the pieces.

The three parts, every time

  • Base case — the smallest input with an immediate answer; write it first, or you get infinite recursion.
  • Work at this level — what you do with the current element.
  • Leap of faith — call on strictly smaller input and assume it returns the correct answer; correctness follows by induction.

The one decision: return up vs accumulate

Ask "is the answer ONE combined value, or MANY enumerated things?" One value (sum, depth, count, boolean) → return it up and combine children's returns. Many things (all paths, subsets, permutations) → accumulate into a shared list, record a copy of the path at the base case, using the do / recurse / undo rhythm.

Templates

# return-up
def solve(node):
    if is_base(node): return base_value
    L = solve(node.a); R = solve(node.b)
    return combine(node, L, R)

# accumulate (do / recurse / undo)
def solve(state, path, result):
    if complete(state):
        result.append(list(path)); return
    for c in choices(state):
        path.append(c)
        solve(advance(state, c), path, result)
        path.pop()

When it applies, and when it does not

Applies to self-similar structure (trees, nested data, "try a choice then solve the rest", divide-and-conquer). Does not apply when there's no smaller sub-instance. If the recursion recomputes the same input repeatedly, that overlap is the signal to add memoization — the bridge to dynamic programming.
