Lesson 01 of the course

The Solving Framework: how to not freeze on a cold problem

You know the algorithms. The thing that breaks down is the first five minutes staring at an unseen LeetCode problem. This lesson gives you a repeatable move set to run in those five minutes, so you're never staring at a blank page again. One tangible win: by the end you'll have a process you can apply to every problem for the rest of this course.

The win A fixed sequence — UPSIR — that converts "I have no idea" into "here are my candidate patterns and why." Plus a signal→pattern table you'll keep reusing.

Why a process at all?

Strong solvers don't "see the answer." They run a search that reliably surfaces the answer. The reason you freeze isn't missing knowledge — it's that your search is unstructured, so working memory floods and you stall. A checklist offloads that load. This is the same reason surgeons and pilots use checklists for things they already know how to do [1].

Deriving the process from first principles

Let's not memorize an acronym. Let's build it by asking: what must be true before I can write correct code? Work backwards.

Derive it

To write code, I need a correct approach. To trust an approach, I need to have dry-run it on a tiny example. To pick an approach, I need candidate techniques. To get candidates, I need to read the signals in the problem. To read signals correctly, I need to understand the problem exactly (inputs, output, constraints, edge cases).

Reverse that chain and you get the order you must work in:

U → P → S → I → R

  1. U — Understand. Restate the problem in one sentence. Nail down input/output types, constraints (the n ≤ ? that decides your target complexity), and 2 edge cases. Most wrong answers are wrong here, not in the code.
  2. P — Probe for signals. Scan for the tells (sorted? substring? "number of ways"? "min/max feasible"?). These map to patterns — the table below is your lookup.
  3. S — Select a pattern (via brute force first). Always state the brute force out loud. Then ask: "what's wasteful here, and which signal tells me how to remove the waste?" That question is pattern selection. (This is the first-principles move we'll use in every lesson.)
  4. I — tiny Input dry-run. Trace your chosen approach on a 3–5 element example by hand before coding. If it breaks here, you just saved 20 minutes.
  5. R — Review / code / test / optimize. Code it, test the edge cases from step U, then ask "can I hit the target complexity from the constraints?"

The constraints→complexity trick (part of U)

The constraint n silently tells you the intended complexity, which narrows the pattern before you even think:

ConstraintTarget complexitySuggests
n ≤ 20O(2ⁿ) / O(n!)backtracking, bitmask subsets

A trap: when the obvious signal lies

Trap

"Find the k-th largest element in an array." The words "k-th largest" scream heap (and a heap works, O(n log k)). But the better answer is Quickselect, O(n) average. Lesson: the signal gives you candidates, not a verdict. Step S still asks "is there less waste?" — here, a heap re-sorts more than needed; partitioning throws away half each time.

This is why UPSIR keeps brute force → "what's wasteful?" at its center. The table starts your search; the waste-question finishes it. That habit is what generalizes to problems the table doesn't cover.

Worked example: full UPSIR on "Trapping Rain Water" (LeetCode Hard 42)

U: input = heights array; output = total trapped water (int). Water above index i = min(maxLeft, maxRight) − height[i], clamped at 0. Edge: empty or strictly increasing array ⇒ 0.

P: each position depends on a max from the left and a max from the right ⇒ smells like precomputed prefix/suffix, or two pointers from both ends.

S: brute force = for each i, scan left and right for maxes → O(n²). Waste = recomputing the same maxes. Remove it two ways: (a) prefix-max + suffix-max arrays → O(n) time, O(n) space; (b) realize the smaller of the two running maxes is the binding constraint, so two pointers moving inward → O(n) time, O(1) space. The two-pointer insight is derived, not memorized: "the shorter wall decides the water, so advance the shorter side."

I: dry-run [0,1,0,2] by hand → 1 unit. R: code the two-pointer version, test [], [3,2,1], confirm O(n).

Notice: a Hard fell out of the same five steps. That's the whole point.

Reference card — the UPSIR checklist

The compressed version. Run this top to bottom on any unseen problem; a 2-minute re-read of this section should reload the whole process.

  1. U — Understand. Restate the problem in one sentence. Pin down the input and output types, read the constraints to infer your target complexity, and write two edge cases. Most wrong answers go wrong here, not in the code.
  2. P — Probe for signals. Scan for the tells (sorted? contiguous substring? "number of ways"? "minimize the maximum"?) and list the candidate patterns they map to.
  3. S — Select. First classify the problem (see the fork below). Then state the brute force and ask: "what is wasteful here, and which signal tells me how to remove the waste?" The answer to that question is your pattern.
  4. I — tiny Input dry-run. Trace your chosen approach by hand on a 3–5 element example before you write any code. If it breaks here, you just saved twenty minutes.
  5. R — Review. Code it, test the edge cases you wrote in step U, then confirm you actually hit the target complexity the constraints implied.
The step-S fork — read this when you can't find a brute force

Not every problem has a slow brute force sitting beneath the pattern. Classify first:

  • Optimization problem (it asks for a min, max, longest, best, or fewest): the brute force really is different from the pattern. State the slow version, find the waste, and the waste reveals the pattern. For example, Koko Eating Bananas: trying every possible eating speed is the slow version, and binary search on that speed is the fast one.
  • Traversal or enumeration problem (it asks you to count, find, or list all of something): there is no slower baseline. The correct traversal is the answer, so "brute force" and "chosen pattern" are the same sentence — just make it concrete. For example, Number of Islands: you visit every cell and flood-fill each group with DFS or BFS; there is no dumber version to improve on.

If you find yourself hunting for a brute force beneath a traversal problem, stop — you were already done at step P.
