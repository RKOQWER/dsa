Grid DP — when the state is a cell (row, col)

When a problem lives on a 2D grid and asks for a best path, a count of paths, or a best region, the DP state is almost always the cell (r, c), and each cell's answer is built from its neighbors (usually up and left). This is the 1D idea lifted into two dimensions. Once you see "I'm at a cell and I came from a bounded set of adjacent cells," the recurrence writes itself.

Deriving grid DP

Take Unique Paths: a robot at the top-left of an m×n grid moves only right or down; count the distinct paths to the bottom-right.

Derive it

Find the choice — but run it backwards. Ask not "where can I go?" but "how could I have arrived at cell (r, c)?" Since moves are only right or down, the only cells that lead into (r, c) are the one directly above (r-1, c) and the one directly to the left (r, c-1).

So the state function is dp(r, c) = the count of paths to cell (r, c), and the transition sums the two cells that feed it:

dp[r][c] = dp[r-1][c] + dp[r][c-1]

with dp on the top row and left column equal to 1 (only one straight-line way to reach them). Spot the overlap: a recursive "count paths from here to the end" would revisit the same cell through many routes; because dp[r][c] is reused by both the cell below it and the cell to its right, caching the grid makes it O(m·n).

The transferable shape: grid DP applies when the state function is the cell dp(r, c) and the transition depends on a fixed, small set of already-computed neighbor cells (classically up and left, sometimes up-left for diagonal moves). You compute the DP by filling the table in an order — row by row, left to right — that guarantees those neighbors are ready before you reach the cell. Because each cell only looks at the previous row and the current row's left neighbor, you can usually compress the table to a single row for O(n) space.

When to reach for grid DP, and why

  • The problem is on a 2D grid and asks for a best path cost, a count of paths, or the best rectangle/region, with movement restricted to a few directions. Restricted movement is what makes the dependency set of each cell small and acyclic, which is exactly what lets you fill a table in one pass instead of searching exponentially many paths.
  • Each cell's answer is a simple combination of its neighbors' answers. If a cell depended on arbitrary far-away cells, a table wouldn't help; the locality (up/left) is the thing that makes it DP rather than a general search.
  • You need the optimal value or a count, not the actual path. If you must output the path itself you can still backtrack through the table afterward, but the DP computes the aggregate first.

The template

# Unique Paths — O(m*n) time, O(n) space (one rolling row)
def uniquePaths(m, n):
    row = [1] * n
    for _ in range(1, m):
        for c in range(1, n):
            row[c] += row[c-1]      # row[c] is "above", row[c-1] is "left"
    return row[-1]

# Min Path Sum — same skeleton, combine with min + the cell's own cost
def minPathSum(grid):
    m, n = len(grid), len(grid[0])
    dp = [[0]*n for _ in range(m)]
    for r in range(m):
        for c in range(n):
            up   = dp[r-1][c] if r else float('inf')
            left = dp[r][c-1] if c else float('inf')
            base = 0 if (r==0 and c==0) else min(up, left)
            dp[r][c] = grid[r][c] + base
    return dp[m-1][n-1]

Composition — a Hard built from grid DP + earlier patterns

Dungeon Game (Hard) — link. Composes grid DP with a reversed fill direction, drawing on the backward-reasoning habit from DP recognition (Lesson 26).

Show the decomposition (try it yourself first)

The problem: a knight starts top-left, moves right/down to the bottom-right, each cell adds or subtracts health; find the minimum starting health so health never drops to 0 or below anywhere.

Why the naive forward grid DP fails: "max health collected so far" at a cell does not determine the future — you could arrive with lots of health but still die later, or arrive lean but survive. The quantity that actually constrains the answer is the health you need going forward, which depends on cells you haven't filled yet.

Pattern A — grid DP, but fill from the destination backward: define dp[r][c] = minimum health needed entering cell (r,c) to survive to the end. Then dp[r][c] = max(1, min(dp[r+1][c], dp[r][c+1]) - dungeon[r][c]). Fill bottom-right to top-left so the neighbors you depend on are already known.

Pattern B — the backward-reasoning idea (Lesson 26): when "what I've accumulated" doesn't capture the future, flip the recurrence to reason from the goal backward. That is the same move that made several recurrences in Lesson 26 click.

The Hard = (grid DP neighbor-combination) + (reverse the fill because the constraint is forward-looking). The grid machinery is this lesson; the reversal is the only new idea.

Reference card — Grid DP

When, and why

Use it on a 2D grid asking for a best path cost, a count of paths, or a best region, with movement restricted to a few directions. Restricted movement keeps each cell's dependency set small and acyclic, so filling a table row by row computes every cell once in O(m·n) instead of searching exponentially many paths.

The three acts, specialized

Define the state function: dp(r, c) = the answer for the cell. Define the transition: express dp(r, c) from the neighbors that feed it (up, left, sometimes up-left), combined by the operator the question demands; if the constraint looks forward, define the transition from the destination backward instead. Compute the DP: fill in an order that computes those neighbors first, and compress to one row for O(n) space when only the previous row is needed.

Template

for r in range(m):
    for c in range(n):
        dp[r][c] = cell_cost(r,c) + combine(dp[r-1][c], dp[r][c-1])
