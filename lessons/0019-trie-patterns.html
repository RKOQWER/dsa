Trie Patterns — deriving the prefix tree from "why am I re-scanning shared prefixes?"

A trie (prefix tree) is the answer to one specific pain: you have many strings and keep asking prefix questions — "does any word start with app?", "insert apple", "is app itself a word?". By the end you'll derive the trie from the waste in the naive approach, and recognize the two tells that should make you reach for it: many strings plus prefix-shaped queries.

Deriving the trie from scratch

Suppose you're building an autocomplete over a dictionary of 100,000 words and must answer "how many stored words start with this prefix?" repeatedly.

Derive it

Brute force: store the words in a list (or a hash set). For each prefix query, scan every word and test word.startswith(prefix) → O(number of words × prefix length) per query. With many queries, that's hopeless. Even a hash set only answers "is this exact word present"; it gives nothing for prefixes, because hashing deliberately scatters similar strings to unrelated buckets.

Spot the waste: the words apple, app, apply all share the prefix app, yet the naive approach re-reads those three letters independently for every word and every query. The shared structure is being recomputed constantly.

The insight (= the trie): store the shared prefix once. Build a tree where each edge is a character and each path from the root spells a prefix. apple, app, and apply share one a → p → p path, then branch. Now "words starting with app" is just "walk the three edges a, p, p and look at everything below" — the walk costs only the prefix length, independent of how many words are stored. A boolean is_end flag on a node marks that a word terminates exactly there (so app can be a stored word even though apple continues past it).

class TrieNode:
    def __init__(self):
        self.children = {}      # char -> TrieNode
        self.is_end = False     # a stored word ends here

class Trie:
    def __init__(self):
        self.root = TrieNode()
    def insert(self, word):
        node = self.root
        for ch in word:                     # walk/create one edge per char
            node = node.children.setdefault(ch, TrieNode())
        node.is_end = True
    def _walk(self, s):                      # follow s; return end node or None
        node = self.root
        for ch in s:
            if ch not in node.children: return None
            node = node.children[ch]
        return node
    def search(self, word):                  # exact word present?
        node = self._walk(word)
        return node is not None and node.is_end
    def startsWith(self, prefix):            # any word with this prefix?
        return self._walk(prefix) is not None

Every trie operation is this same walk: follow one edge per character. Insert creates missing edges; search/startsWith just follow existing ones. The whole data structure exists to make prefixes O(length-of-query) instead of O(number-of-words).

When to reach for a trie, and why it works

Reach for a trie when both tells are present: you have a collection of many strings (a dictionary, a word list, a set of numbers viewed as bit-strings) and the queries are prefix-shaped — "starts with", autocomplete, "insert/search a word", "does any word match this pattern with wildcards", or "find the pair with maximum XOR" (where numbers become fixed-length bit strings and you greedily chase the opposite bit). The deciding signal is the word "prefix" or repeated structural overlap among the strings. It works because storing shared prefixes once turns every query into a single root-to-node walk costing only the query's length, completely independent of how many strings are stored — the cost a hash set can never give you for prefixes, because hashing destroys the ordering and adjacency that prefixes rely on.

Do not reach for a trie when you only ever test exact-match membership (a hash set is simpler and lighter) or when there are few strings (the naive scan is fine and the trie's pointer overhead isn't worth it). A trie trades memory for prefix speed; if you aren't asking prefix questions, you're paying that memory for nothing.

Trap — the is_end flag and the wildcard branch

Two things catch people. First, forgetting is_end: without it you can't distinguish a stored word from a mere prefix of a longer word, so search("app") wrongly returns true just because apple exists. Second, when a query allows a wildcard (. matching any character, as in "Add and Search Word"), a single downward walk is no longer enough — at a . you must branch into all children and recurse, turning the walk into a small DFS. Recognizing that a wildcard converts the linear walk into a branching search (recursion, Lesson 14) is the key to that problem.

Composition — how a Hard is built from this pattern

Word Search II (Hard 212) — link — composes a trie (this lesson) with backtracking on a grid (Lesson 15) and the matrix-as-graph DFS traversal (Lesson 9). Try it before opening the decomposition.

Show the decomposition (try it yourself first)

Given a board of letters and a list of words, find every word that can be traced along adjacent cells. The naive approach — run Word Search (backtracking) once per word — repeats work badly when words share prefixes: you re-explore the same a → p → p board paths for apple, app, and apply separately.

Piece A (trie, this lesson): build one trie of all target words. Now a single grid walk can check all words at once: as you step from cell to cell, you also step down the trie by that cell's letter. If a letter isn't a child of the current trie node, every remaining word down this board path is impossible — prune immediately. Shared prefixes are explored only once.

Piece B (backtracking on a grid, Lesson 15): the board walk is the do/recurse/undo rhythm — mark a cell visited, recurse into its neighbours, then unmark on the way back. The trie node you're at travels alongside the recursion as extra state.

Piece C (matrix traversal / 4-directional neighbours, Lesson 9): the "adjacent cells" movement is the standard up/down/left/right grid DFS from the matrix lesson, with bounds checks.

def findWords(board, words):
    root = {}                              # trie as nested dicts (this lesson)
    for w in words:
        node = root
        for ch in w: node = node.setdefault(ch, {})
        node['$'] = w                      # store the full word at its end
    rows, cols, found = len(board), len(board[0]), set()
    def dfs(r, c, node):                   # backtracking (Lesson 15)
        ch = board[r][c]
        if ch not in node: return
        nxt = node[ch]
        if '$' in nxt: found.add(nxt['$'])
        board[r][c] = '#'                  # mark visited (do)
        for dr, dc in ((1,0),(-1,0),(0,1),(0,-1)):   # 4-dir (Lesson 9)
            nr, nc = r+dr, c+dc
            if 0 <= nr < rows and 0 <= nc < cols and board[nr][nc] != '#':
                dfs(nr, nc, nxt)
        board[r][c] = ch                   # unmark (undo)
    for r in range(rows):
        for c in range(cols):
            dfs(r, c, root)
    return list(found)

The Hard = (trie to check all words in one pass) + (grid backtracking) + (4-directional matrix traversal). Three patterns you already own, stacked. Name the pieces and the Hard stops being hard.

Reference card — Trie (Prefix Tree)

The compressed version. A 2-minute re-read should reload the whole pattern.

When to use it, and why

Use when you have many strings AND prefix-shaped queries: starts-with, autocomplete, insert/search a word, wildcard matching, or max-XOR (numbers as bit-strings). It works by storing each shared prefix once, so a query is a single root-to-node walk costing only the query length, independent of how many strings are stored — something a hash set cannot do for prefixes. Skip it for exact-match-only (use a set) or when there are few strings.

The structure and the one operation

Each node holds children (char → node) and an is_end flag. Every operation is the same walk: follow one edge per character. Insert creates missing edges and sets is_end; search follows edges and checks is_end; startsWith follows edges and checks you didn't fall off.

Template

root = {}
def insert(word):
    node = root
    for ch in word: node = node.setdefault(ch, {})
    node['$'] = True                 # mark end
def walk(s):
    node = root
    for ch in s:
        if ch not in node: return None
        node = node[ch]
    return node
# search: walk(word) and '$' in it ; startsWith: walk(prefix) is not None

Two traps

Keep the is_end/'$' marker or you can't tell a word from a prefix. A wildcard query (.) turns the single walk into a branching DFS over all children at that node.
