DP Recognition — every DP is three acts: define the state, define the transition, compute the DP

Dynamic programming is the single biggest interview filter, and it is where most people freeze. The cure is to stop thinking of DP as a bag of tricks and start treating it as three mechanical acts, always in the same order: define the state function, define the transition function, then compute the DP. Every DP you will ever write is nothing more than these three acts applied to a harder problem. By the end of this lesson you will be able to look at a problem and derive whether DP applies — not recall whether you've seen it.

Deriving DP from a brute-force recursion

Take the cleanest possible case: Fibonacci. fib(n) = fib(n-1) + fib(n-2). Write the obvious recursion and watch what goes wrong.

Derive it

Brute force:

def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)

Spot the waste: draw the call tree for fib(5). fib(3) is computed twice, fib(2) three times, fib(1) five times. The tree has roughly 2ⁿ nodes, but there are only n distinct subproblems: fib(0)…fib(n). We are re-solving the same handful of subproblems an exponential number of times. That gap — few distinct subproblems, re-solved endlessly — is the entire signal for DP.

The insight (= the pattern): cache each subproblem's answer the first time you compute it, and return the cache on every later call. The call tree collapses to n unique computations.

from functools import cache
@cache
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)   # now O(n)

That's it. DP is nothing more than recursion plus a memory of answers you've already computed. The three acts just name that move precisely: the recursive function is the state function, its recurrence is the transition function, and adding the memory is how you compute the DP. Every DP you will ever write is this applied to a harder problem.

The two conditions, stated so you can test for them

A problem is DP exactly when both of these hold, and you can check them from the problem statement:

  • Optimal substructure. The answer to the whole problem can be built from answers to strictly smaller versions of the same problem. Concretely: you can describe a choice at the current step such that, after making it, what remains is a smaller instance of the identical problem. If you cannot phrase "make one choice, then I face a smaller version of the same problem," it is not DP.
  • Overlapping subproblems. Those smaller versions are reached again and again through different choice sequences. This is what makes caching pay off — if every subproblem were distinct, caching would save nothing and plain recursion or greedy would do.

The Universal First Principles Rule

A Dynamic Programming state is just a representation of a specific point in time. To find your state variables, you must put yourself in the shoes of a machine building the solution step-by-step and ask yourself exactly two questions:

  1. Progress Variable: Where am I in the process? (What index, remaining length, or choice number am I on?)
  2. Constraint / Context Variables: What information from the past dictates my legal choices for the future?

This second question is where you were getting stuck. If a past decision restricts what you can legally do next, that piece of information must become a state variable. If it doesn't restrict future choices, it is completely irrelevant and should be ignored.

The recipe — the same three acts for every DP

Once you suspect DP, you never improvise. You perform these three acts, in order, every time. They are written as things you do, not facts to memorize.

  1. Define the state function. Decide the minimal set of parameters such that dp(those parameters) is the answer to exactly one subproblem — the smallest set of values for which two calls with the same values must return the same answer. For Fibonacci it is just n, so dp(n) is "the n-th Fibonacci number." For a walk through an array it is usually an index i, meaning "the subproblem on the suffix starting at i." The smallest states — the ones whose answer you know without recursing, like an empty suffix, an index past the end, or n < 2 — are the base cases, and you pin them down here, while defining the function, not as a separate step. Getting this act right is 80% of the work; everything else follows.
  2. Define the transition function. At the current state, enumerate every choice you could make. Each choice consumes part of the problem and leaves a smaller state, so you write dp(state) in terms of dp(smaller states) — that equation is the transition (the recurrence). The operator that combines the sub-answers is dictated by what the question asks for: max/min for a best value, + for a count of ways, or for feasibility.
  3. Compute the DP. Evaluate the state function over all states. How you evaluate it is a single free choice, not a new idea: you can memoize (top-down — follow the transition literally and cache each state the first time you compute it) or tabulate (bottom-up — fill a table in an order where every state's dependencies are ready before it). Both run the exact same two functions you just defined; you pick whichever is more convenient for the problem.

The two ways to compute — which, and why

Act 3 has two implementations of the identical state and transition functions, so pick by convenience, not correctness. Top-down memoization is easier to write because it follows the transition literally and only computes states you actually reach, which matters when the state space is large but sparsely used. Bottom-up tabulation is worth the extra thought when you want to drop the recursion stack (deep states can overflow it) or when you can see that each state only depends on the previous row, which lets you throw the rest of the table away and run in O(1) extra space.

The template (reproduce from memory)

# ACT 3, first way to compute — MEMOIZE (top-down): the shape of nearly every DP you'll write
from functools import cache

def solve(problem):
    @cache
    def dp(state):                          # the STATE function (act 1)
        if is_base(state):
            return base_value(state)        # base cases = the smallest states
        best = NEUTRAL                      # 0 / -inf / +inf depending on combine
        for choice in choices(state):       # the TRANSITION function (act 2)
            sub = dp(next_state(state, choice))
            best = combine(best, value(choice) + sub)
        return best
    return dp(initial_state)

# ACT 3, second way to compute — TABULATE (bottom-up): same state + transition, filled in dependency order
def solve_table(n):
    dp = [base for _ in range(n + 1)]
    for i in range(first_unknown, n + 1):
        dp[i] = combine_over_choices(dp, i)
    return dp[n]

Composition — a Hard built from DP + an earlier pattern

Russian Doll Envelopes (Hard) — link. This composes DP (Longest Increasing Subsequence) with sorting as a tool (Lesson 11) and binary search (Lesson 10).

Show the decomposition (try it yourself first)

The problem: an envelope fits in another only if both width and height are strictly larger. Find the longest chain of nesting envelopes. Two dimensions must both increase.

Pattern A — sorting as a tool (Lesson 11): sort by width ascending. Now one dimension is handled: any valid chain reads left-to-right in this order. But ties in width are a trap — two equal widths can't nest, so for equal widths sort height descending, which prevents the algorithm from ever picking two same-width envelopes in the same increasing run.

Pattern B — reduce to a known 1-D problem: after sorting, the answer is the Longest Increasing Subsequence of the heights alone. The width constraint is already enforced by the sort order, so a classic LIS on heights solves it.

Pattern C — binary search (Lesson 10) to make LIS fast: the O(n²) DP for LIS is too slow here; the O(n log n) LIS keeps a "tails" array and uses binary search to place each height. That is DP's recurrence accelerated by binary search over the tails.

The Hard = (sort to kill one dimension) + (LIS recurrence) + (binary search to speed LIS). Each piece you already own. Naming the three pieces is the whole battle.

Your reps

  1. For every practice problem, define the state function and the transition function on paper before coding. If you can do those two acts, computing the DP is mechanical.
  2. Take one problem you computed top-down (memoized) and recompute it bottom-up (tabulated), then shrink its memory. Act 3 is the only thing that changes; doing this once makes the two ways of computing permanent.

Reference card — DP Recognition

Re-read this and the whole recipe should reload.

When it is DP, and why

  • Optimal substructure: you can phrase "make one choice now, then face a smaller version of the same problem." The whole answer is built from answers to smaller identical problems.
  • Overlapping subproblems: those smaller problems recur through different choice paths, so caching each one turns exponential work into polynomial. If subproblems never repeat, it is not DP (it is greedy, divide-and-conquer, or plain recursion).

The recipe (same three acts every time)

  1. Define the state function — the minimal parameters for which dp(params) is one subproblem's answer; its smallest states are the base cases, pinned down here.
  2. Define the transition function — enumerate the choice at the current state and write dp(state) in terms of dp(smaller states), combined by the operator the question demands.
  3. Compute the DP — evaluate the function over all states, either by memoizing top-down or tabulating bottom-up (and shrinking memory). This choice is an implementation detail of this one act, not a separate step.

How to combine sub-answers

Use max or min for "best value" problems, + for "count the ways" problems, and or for "is it possible" problems. The combine operator is dictated by what the question asks for.

Template

from functools import cache
@cache
def dp(state):
    if base(state): return base_value
    return combine(value(c) + dp(next(state, c)) for c in choices(state))
