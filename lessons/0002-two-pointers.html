Deriving two pointers from scratch

Take the cleanest possible case. Sorted array, find whether two numbers sum to a target.

Classify first (your new step-S habit): this is "find a pair that works" — an existence/search question, and it does have a slow brute force. So it's the optimization kind: state brute force, hunt the waste.

Derive it

Brute force: every pair (i, j) → O(n²). On [1, 2, 4, 7, 11], target 9: try 1+2, 1+4, 1+7, 1+11, 2+4…

Spot the waste: the array is sorted, and brute force ignores that entirely. When 1+11 = 12 overshoots the target 9, brute force shrugs and tries 1+2 next. But think: 11 is the largest element. Paired with the smallest (1) it already overshoots — so 11 can't pair with anything bigger either. The sortedness told me something and I threw it away.

The insight (= the pattern): put one pointer at each end. Look at a[lo] + a[hi]:

  • too big → the only way to get smaller is move hi left (every other element on the right is even bigger).
  • too small → move lo right.
  • equal → found it.

Each step provably eliminates a whole row/column of the brute-force grid. Pointers only move inward → O(n), O(1) space. That convergence IS the two-pointer pattern. It fell out of "sorted + find a pair," not from memory.

The deeper principle (so it transfers)

Two pointers works whenever moving a pointer has a monotonic, predictable effect on some quantity, so you always know which pointer to move. Sorted-pair-sum is the obvious case; the same logic powers palindrome checks (ends inward), container-with-water (shorter wall moves), and fast/slow cycle detection. If moving a pointer doesn't give you reliable directional information, two pointers won't apply — that's your discrimination test.

How to DERIVE two pointers cold — the intuition to remember

When you've never seen the problem and only have a brute force over all pairs, these two questions turn it into two pointers by yourself:

  1. Can I evaluate one pair that proves other pairs are useless? Brute force collapses to O(n) only when checking one pair lets you discard many without looking. So start at the two extremes and ask at each step: "if I move this pointer, am I throwing away pairs that were provably no better?" Move that pointer. The pattern is really a proof of elimination, not a trick.
  2. If the answer depends on TWO factors, max out one for free, then you only fight over the other. In Container With Most Water the area is width × min(height) — two factors. You can't control height, but you can max width instantly by starting the pointers at both ends. Now width can only shrink, so the only way to ever do better is to improve the other factor, height — which means abandoning the shorter line (it's the bottleneck capping the height). Moving the taller line shrinks width and can't raise the capped height → provably useless. So move the short one.

The one sentence to keep: start at the extremes; at every step move the pointer whose move discards only pairs you've proven can't win — and when two factors make the answer, fix one at its best so you fight over just one.

The signals (step P)

There are three distinct flavors of two pointers. They are not interchangeable — each solves a different shape of problem. Here is each one explained in full, so you understand why it fits, not just that it does.

Flavor 1 — Opposite ends, converging inward

You start one pointer at the left end of a sorted array and one at the right end, and you move them toward each other. You use this when the problem asks you to find a pair (or triple) of elements with some target sum or property. It works because the array is sorted: by comparing the current pair's sum against the target, you always know which direction gets you closer, so you can discard one candidate per step instead of checking all pairs. Palindrome-checking is the same flavor — you compare the character at the left end with the character at the right end and walk both inward, because a palindrome is defined by that mirror symmetry.

Flavor 2 — Same direction, a slow "write" pointer trailing a fast "read" pointer

Both pointers start at the front and move the same way, but at different speeds. The fast pointer reads every element; the slow pointer marks where the next kept element should be written. You use this when the problem asks you to modify an array in place — remove a value, deduplicate, or partition it (as in Dutch-national-flag / Sort Colors). It works because you're compacting the "good" elements to the front while the fast pointer scans ahead, so you never need a second array.

Flavor 3 — Fast & slow (Floyd's tortoise and hare)

One pointer advances one step at a time, the other advances two steps at a time. You use this on linked lists to find the middle node, detect a cycle, or find the k-th node from the end. It works because the two pointers move at a fixed ratio: when the fast one reaches the end, the slow one is exactly halfway; and if there's a cycle, the fast one eventually laps the slow one and they collide.

A special case of Flavor 1 — "move the limiting side"

When the problem is "maximize an area" or "optimize some value computed from a pair of positions" (Container With Most Water is the classic), you still start at both ends, but the rule for which pointer to move changes: you move the pointer on the limiting side (the shorter wall), because that's the only move that could possibly improve the result. We derive exactly why this is safe in the practice section below.

The template (reproduce from memory)

# Opposite-ends converge (sorted array, find a pair summing to target)
def two_sum_sorted(a, target):
    lo, hi = 0, len(a) - 1
    while lo < hi:
        s = a[lo] + a[hi]
        if s == target:
            return (lo, hi)
        elif s < target:
            lo += 1          # need bigger -> move left pointer right
        else:
            hi -= 1          # need smaller -> move right pointer left
    return None

# Same-direction (slow/fast): in-place remove, keep order
def remove_val(a, val):
    slow = 0
    for fast in range(len(a)):
        if a[fast] != val:
            a[slow] = a[fast]
            slow += 1
    return slow              # new length; a[:slow] is the kept prefix

Trap — sharpen your discrimination

Two Sum (the original, Easy 1) on an unsorted array. The "find a pair summing to target" phrasing screams two pointers — but the array isn't sorted, and sorting destroys the original indices the problem asks you to return. Here the right tool is a hashmap (seen-value → index), O(n). Lesson: two pointers needs the monotonic directional signal (usually from sortedness). Remove that, and the signal is lying to you. Always confirm the precondition, don't just match keywords.

Composition — how a Hard is built from this pattern

Recall from Lesson 1: hards are usually two patterns stacked. Trapping Rain Water (Hard 42) — link — composes two-pointers with the prefix/suffix-max idea.

Show the decomposition (try it yourself first)

Water over position i = min(maxLeft, maxRight) − height[i]. Brute force recomputes both maxes per position → O(n²).

Pattern A (prefix/suffix): precompute left-max and right-max arrays → O(n) time, O(n) space.

Pattern B (two pointers) removes the extra space: keep lo, hi at the ends with running maxL (tallest seen from the left) and maxR (tallest seen from the right). The subtle unlock: at lo you know maxL exactly, but not the true right-max — yet you don't need it. Water is capped by the shorter wall (min of the two). When maxL < maxR, the real right wall for lo is at least maxR, so it's taller than maxL, so min picks maxL — the left side is provably the binding wall and you can finalize water = maxL − height[lo] right now, without having scanned the whole right side. Then move lo inward. Symmetrically settle hi when the right side is shorter. O(n) time, O(1) space.

Why "move the shorter side" here differs from Container With Most Water: same action, different reason. In Container, you move the shorter line because it's the only move that could improve the area. Here, you settle the shorter side because it's the side whose water is already provable — min makes the taller side's still-unknown exact max irrelevant. Spotting that the same move can rest on different proofs is a real skill.

def trap(height):
    lo, hi = 0, len(height) - 1
    maxL = maxR = total = 0
    while lo < hi:
        if height[lo] < height[hi]:      # left side is the binding wall
            maxL = max(maxL, height[lo])
            total += maxL - height[lo]
            lo += 1
        else:                            # right side is the binding wall
            maxR = max(maxR, height[hi])
            total += maxR - height[hi]
            hi -= 1
    return total

The Hard = (water formula insight) + (two-pointer "settle the provable side"). Neither piece is hard alone. That's the whole method for hards: name the pieces.

Reference card — Two Pointers

The compressed version. If you've forgotten this pattern weeks from now, re-reading just this section should reload it.

When to use it, and why

  • Opposite ends, converging inward. On a sorted array, to find a pair/triple with a target sum or to check a palindrome. The sort tells you which pointer to move to get closer, so you discard one candidate per step instead of checking all pairs.
  • Same direction (slow write, fast read). To modify an array in place — remove, deduplicate, or partition. The fast pointer scans every element; the slow pointer marks where the next kept element is written.
  • Fast & slow (tortoise and hare). On a linked list, to find the middle, detect a cycle, or find the k-th node from the end. The fixed 1-step vs 2-step ratio is what makes it land where you need.
  • Opposite ends, move the limiting side. For "maximize an area / optimize a value from a pair of positions" (Container With Most Water). Move the pointer on the shorter side, because that is the only move that can improve the result.

The one-line reason it works

Moving a pointer has a monotonic, predictable effect on some quantity, so you always know which pointer to move — and each move eliminates a whole slab of the O(n²) brute-force grid, bringing it down to O(n).

How to derive it cold (the two intuitions)

  • Pairs → elimination. Start at the two extremes and move the pointer whose move discards only pairs you can prove are no better. Two pointers is a proof of elimination, not a trick.
  • Two factors → fix one. If the answer is built from two factors (e.g. width × height), max one out for free by starting at the ends, so you only ever fight over the other. The bottleneck factor (the shorter line) is the one to abandon — moving the other can't help.

Discrimination test (when it does NOT apply)

If moving a pointer gives you no reliable directional information — for example "find a pair summing to target" on an unsorted array, or a problem where you must preserve original indices — two pointers does not apply. Reach for a hashmap instead. Match the precondition, not the keywords.

Templates (Python)

# opposite ends — sorted pair sum
lo, hi = 0, len(a) - 1
while lo < hi:
    s = a[lo] + a[hi]
    if s == target: return (lo, hi)
    elif s < target: lo += 1
    else: hi -= 1

# same direction — in-place keep
slow = 0
for fast in range(len(a)):
    if keep(a[fast]):
        a[slow] = a[fast]; slow += 1
# a[:slow] is the result

# fast & slow — linked list cycle
slow = fast = head
while fast and fast.next:
    slow = slow.next; fast = fast.next.next
    if slow is fast: return True
return False

Complexity and classic problems

Time O(n), or O(n log n) if you must sort first (as in 3Sum). Space O(1).
