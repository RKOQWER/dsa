Deriving the interval pattern from scratch

Take the cleanest case. You're given a list of intervals [start, end] in arbitrary order; merge all overlapping ones.

Derive it

Brute force: repeatedly compare every interval against every other, merging any pair that overlaps, and loop until no more merges happen. That's at least O(n²) and the "loop until stable" control flow is error-prone.

Spot the waste: the chaos comes entirely from the intervals being in random order — you never know where an overlapping partner might be, so you must check all pairs. But overlap has structure you're ignoring: if two intervals overlap, one's start lies inside the other. The disorder is forcing you to search in both directions when the relationship is fundamentally about ordering on the number line.

The insight (= the pattern): sort the intervals by start. Now any interval can only overlap with the one immediately before it in sorted order — because everything earlier has a start ≤ the current start, so the only question is whether the running merged interval's end reaches the current start. Walk left to right, extending the current merged interval's end when the next interval starts before that end, otherwise closing it off and opening a new one. One sort plus one linear pass: O(n log n). Sorting converted a two-directional search into a single forward sweep.

The deeper principle (so it transfers)

Almost every interval problem begins with a sort, because sorting imposes the one-directional structure that makes overlaps local — once sorted, you only ever compare an interval with the "current" context rather than with all others. The decision that remains is what to sort by. Sort by start when you are merging or sweeping left to right and asking "does this one overlap what I've accumulated so far." Sort by end when you are greedily keeping as many non-overlapping intervals as possible (activity selection), because finishing earliest leaves the most room for the rest. A third view, the sweep line, forgets intervals as objects and instead sorts their endpoints as +1 (an interval starts) and −1 (an interval ends) events; running a counter across the sorted events tells you how many intervals are active at any moment, which answers "maximum overlap" questions directly.

When to use each variant, and why

Sort by start, then sweep to merge or coalesce

You sort by start when the task is to merge overlapping intervals, insert a new interval into a sorted set, or detect whether any two overlap. After sorting, you keep a single running interval and compare each next interval's start against the running end; if it reaches inside, you extend, otherwise you emit the running one and start fresh. It works because, in start order, the only possible overlap for the current interval is with the accumulated block to its left.

Sort by end for greedy non-overlap selection

You sort by end when you want the maximum number of mutually non-overlapping intervals, or the minimum number of intervals to remove so the rest don't overlap. You repeatedly take the interval that finishes earliest among those still compatible, because an early finish frees up the most remaining room. It works by an exchange argument: any optimal solution can be rewritten to start with the earliest-finishing interval without getting worse.

Sweep line over endpoint events

You use a sweep line when the question is about how many intervals are simultaneously active — maximum concurrent meetings, the point of greatest overlap, or free gaps across many schedules. You turn each interval into a start event (+1) and an end event (−1), sort all events by position, and run a counter; the counter's peak is the maximum overlap, and stretches where it is zero are the gaps. It works because the count of active intervals only changes at endpoints, so scanning the sorted endpoints reconstructs the whole timeline.

The template (reproduce from memory)

# Merge overlapping intervals: sort by start, sweep once
def merge(intervals):
    intervals.sort(key=lambda iv: iv[0])
    out = [intervals[0]]
    for s, e in intervals[1:]:
        if s <= out[-1][1]:          # overlaps the running block
            out[-1][1] = max(out[-1][1], e)
        else:
            out.append([s, e])
    return out

# Max non-overlapping intervals: sort by end, greedy keep
def max_nonoverlap(intervals):
    intervals.sort(key=lambda iv: iv[1])
    count = 0
    cur_end = float('-inf')
    for s, e in intervals:
        if s >= cur_end:             # compatible with last kept
            count += 1
            cur_end = e
    return count

# Sweep line: maximum number of overlapping intervals
def max_overlap(intervals):
    events = []
    for s, e in intervals:
        events.append((s, 1))        # start adds one
        events.append((e, -1))       # end removes one
    events.sort()
    active = best = 0
    for _, delta in events:
        active += delta
        best = max(best, active)
    return best

Composition — how a Hard is built from this pattern

Employee Free Time (Hard) — link — composes interval merging (this lesson) with a merge of sorted sequences (the converging/merge idea from Lesson 2's two-pointer family).

Show the decomposition (try it yourself first)

The ask: given each employee's sorted busy intervals, return the gaps where everyone is free. Common free time is the complement of the union of all busy intervals.

Piece A — flatten and order: you need all busy intervals in a single start-sorted stream. Since each employee's list is already sorted, combining them is a k-way merge — the same "advance the pointer on the smallest front element" logic as merging sorted lists, a direct relative of Lesson 2's two-pointer merge.

Piece B — merge intervals and read the gaps: sweep the start-sorted busy intervals exactly as in this lesson, coalescing overlaps into maximal busy blocks. Whenever the next block starts strictly after the running block ends, the space between them is a free interval for everyone. Emit those gaps.

The Hard = (k-way merge of sorted interval lists) + (merge-overlapping sweep reading gaps). Both halves are patterns you already hold.

Reference card — Interval Patterns

When to use each, and why

  • Sort by start, sweep to merge. Merging overlaps, inserting an interval, detecting any overlap. Keep one running interval; extend it when the next start reaches inside its end, else emit and restart. In start order, overlap can only be with the accumulated block to the left.
  • Sort by end, greedy keep. Maximum non-overlapping set, or minimum removals. Repeatedly take the earliest-finishing compatible interval, because finishing early leaves the most room — provable by an exchange argument.
  • Sweep line over endpoint events. Maximum concurrent intervals, peak overlap, or free gaps. Turn intervals into +1 start and −1 end events, sort, run a counter; the peak is max overlap, zeros are gaps, because the active count only changes at endpoints.

The one-line reason it works

Sorting imposes one-directional order on the number line, which makes overlap local — so a two-directional all-pairs search collapses into a single forward sweep comparing each interval only with the current running context.

Discrimination test

The whole family depends on being able to order the intervals; the only real decision is the sort key (start for merging, end for greedy non-overlap). If the problem is about counting how many are active at once rather than coalescing them, switch to the endpoint sweep-line view.
