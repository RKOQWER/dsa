Meet in the Middle — when the exponential is too big for brute force but the input is tiny

Sometimes no polynomial trick exists: the problem genuinely asks you to search over subsets, and a DP on the sum would need a table too wide to build (sums up to 109, not a few thousand). You're staring at 240 subsets, which is a trillion — too many to enumerate. "Meet in the middle" is the escape hatch: split the input into two halves, brute-force each half independently (2n/2 each, which is only a million when n = 40), then combine the two halves cleverly instead of pairing every left subset with every right subset. The signature tell is a small n (around 30-40) with values far too large for a sum-indexed DP.

Deriving meet in the middle via Closest Subsequence Sum

Take Closest Subsequence Sum (LeetCode 1755): given nums (length n ≤ 40) and a goal, choose any subsequence so that its sum is as close to goal as possible; return the minimum possible |sum − goal|. Note the values can be huge (up to 109 in magnitude).

Derive it

Brute force: enumerate all 2n subsets, compute each sum, track the closest to goal. With n = 40 that is 240 ≈ 1012 subsets — hopeless.

Why the usual DP escape fails. Subset-sum problems (Lesson 28) usually become a DP indexed by the running sum. But here sums range over roughly ±4·1010; you cannot build a table that wide. The DP trick is dead because the value space, not the item count, is the enemy. So we're stuck with an exponential in n — the question becomes: can we make the exponent smaller?

Spot the structure. 240 is impossible, but 220 ≈ 106 is trivial. What if we split the array into two halves of 20 each? Every subset of the whole array is exactly "some subset of the left half" plus "some subset of the right half." So enumerate all 220 left-subset sums into a list L, and all 220 right-subset sums into a list R. Each list is only a million entries.

The naive combine is still 2n. If you pair every left sum with every right sum you're back to 106 × 106 = 1012. The whole win would evaporate. So the combine step must be smarter than a double loop.

The insight (= the pattern): fix a left sum a. The best total using it is a + b where b is a right sum, and we want a + b as close to goal as possible — i.e. we want the right sum b closest to goal − a. If R is sorted, "the value closest to goal − a" is one binary search (Lesson 10's closest-element move). So: sort R once (O(2n/2 log), then for each of the 2n/2 left sums do one O(log) binary search. Total O(2n/2 · n) — a million log-searches, instantly feasible. The exponent went from n to n/2; that halving is the entire pattern.

from bisect import bisect_left

def subset_sums(arr):
    sums = [0]
    for x in arr:                      # each element doubles the set of reachable sums
        sums += [s + x for s in sums]  # 2^len(arr) sums total
    return sums

def min_abs_difference(nums, goal):
    mid = len(nums) // 2
    L = subset_sums(nums[:mid])         # 2^(n/2) left sums
    R = sorted(subset_sums(nums[mid:])) # 2^(n/2) right sums, sorted for binary search
    best = float('inf')
    for a in L:
        need = goal - a                 # want b closest to this
        i = bisect_left(R, need)
        for b in (R[i-1] if i > 0 else None, R[i] if i < len(R) else None):
            if b is not None:
                best = min(best, abs(a + b - goal))
    return best

You didn't recall "meet in the middle" — you asked "can I shrink the exponent?", split the work in half, and then noticed the combine step is just a closest-value lookup, which a sorted array answers by binary search. The splitting plus the sorted-combine is the pattern.

The transferable shape: the two halves give you two sets of partial answers; the art is the combine. The combine is always "for each left partial, find the matching right partial(s) fast," and the matching is done by whichever Lesson-2/5/10 tool fits the relation you need: binary search on a sorted R for "closest to / ≤ a target" (this problem), a hash set/map of R for "exactly equals a target" (counting pairs that sum to K), or two pointers across sorted L and R for "count pairs with sum ≤ K." Same split, different combine.

When to reach for meet in the middle, and why

  • The problem is genuinely a subset / subsequence / assignment search (each element is independently in-or-out, or picked from a few choices), and n is small — around 30 to 40 — so 2n is too big but 2n/2 is fine. That specific size window is the loudest signal: n ≤ 20 you'd just brute-force the whole thing; n in the thirties with "choose a subset" is almost a tell for this technique, because halving the exponent is exactly the room you have.
  • A sum-indexed DP (Lesson 28) is blocked because the values are huge (sums up to 109), so there's no small table to fill. When the obstacle is the magnitude of the values rather than the count of items, the pseudo-polynomial DP dies and you fall back to enumerating subsets — meet in the middle is how you make that enumeration affordable by splitting it.
  • After splitting, the two halves combine through a clean pairwise relation — "closest to", "equals", "at most" a target. You need the combine to be a fast lookup, not another full pairing; if R is sorted or hashed, each left partial finds its match in O(log) or O(1), which is what turns 2n/2 × 2n/2 back down to 2n/2 · log. If the two halves can't be matched by such a lookup, the technique doesn't buy you anything.
  • Each element has k > 2 independent choices (not just in/out), and kn is too big but kn/2 is fine. The split isn't limited to subsets: anything where the global answer factors as "a choice over the left half" combined with "a choice over the right half" admits the same halving, as long as the combine stays a fast lookup.

The templates

from bisect import bisect_left, bisect_right

# Generate all 2^len(arr) subset sums of a half.
def subset_sums(arr):
    sums = [0]
    for x in arr:
        sums += [s + x for s in sums]
    return sums

# COMBINE by "closest to target": want left+right nearest to goal.
def closest(nums, goal):
    m = len(nums) // 2
    L = subset_sums(nums[:m])
    R = sorted(subset_sums(nums[m:]))
    best = float('inf')
    for a in L:
        t = goal - a
        i = bisect_left(R, t)
        for b in (R[i-1] if i else None, R[i] if i < len(R) else None):
            if b is not None:
                best = min(best, abs(a + b - goal))
    return best

# COMBINE by "exactly equals target": count subsets summing to K.
def count_eq(nums, K):
    from collections import Counter
    m = len(nums) // 2
    L = Counter(subset_sums(nums[:m]))
    R = Counter(subset_sums(nums[m:]))
    return sum(cntA * R.get(K - a, 0) for a, cntA in L.items())

# COMBINE by "at most target": count pairs with left+right <= K (two pointers).
def count_leq(nums, K):
    m = len(nums) // 2
    L = sorted(subset_sums(nums[:m]))
    R = sorted(subset_sums(nums[m:]))
    total, j = 0, len(R) - 1
    for a in L:                 # L ascending, R pointer sweeps down
        while j >= 0 and a + R[j] > K:
            j -= 1
        total += j + 1
    return total

Composition — a Hard built from meet-in-the-middle + earlier patterns

Partition Array Into Two Arrays to Minimize Sum Difference (LeetCode 2035, Hard) — link. Composes this lesson's split-and-combine with bitmask subset enumeration (Lesson 13), sorting as preprocessing (Lesson 11), and binary search for the closest element (Lesson 10).

Show the decomposition (try it yourself first)

The problem: you have 2n numbers; split them into two groups of exactly n each to minimize the absolute difference of the two group sums. Here n ≤ 15, so 2n ≤ 30.

Reframe: let S be the total sum. If one group has sum s, the other has S − s and the difference is |S − 2s|, minimized when s is as close to S/2 as possible. So we want a size-n subset whose sum is closest to S/2 — a "closest-to-target" subset problem, but with the twist that the subset must have exactly n elements.

Pattern A — split into halves and enumerate by popcount (meet-in-the-middle + bitmask, Lessons 13 + this one): the chosen group takes some i elements from the left half and n − i from the right half. So enumerate the left half's subsets (2n via bitmasks) bucketed by how many elements they use — leftSums[i] = all sums of left-subsets of size i — and likewise bucket the right half's sums by size. The size buckets are what handle the "exactly n total" constraint; it's the same split as Closest Subsequence Sum, refined by popcount.

Pattern B — sort each right bucket, then binary-search the closest complement (Lessons 11 + 10): for a left sum a that used i elements, you need a right sum from bucket n − i that makes a + b closest to S/2 — i.e. the value in rightSums[n−i] closest to S/2 − a. Sort each right bucket once (Lesson 11), then each lookup is one binary search for the straddling neighbors (Lesson 10).

The Hard = (meet-in-the-middle split, with bitmask enumeration bucketed by popcount to enforce the size-n constraint) + (sort each complement bucket, then binary-search for the closest reachable sum). Peel off the "exactly n each" wording and it's Closest Subsequence Sum wearing a popcount constraint — which is exactly how composed hards tend to look.

Reference card — Meet in the Middle

When, and why

Use it when the problem is a genuine subset/assignment search, n is small (≈30-40) so 2n is too big but 2n/2 is fine, and a sum-indexed DP is blocked because the values are huge. Splitting the input into two halves halves the exponent; the global answer always factors as "a choice over the left half" combined with "a choice over the right half." The payoff only lands if the combine is a fast lookup, not a second full pairing.

The move

Split into two halves. Enumerate all 2n/2 partial results of each (subset sums via bitmask or doubling). Then combine: for each left partial, find the matching right partial(s) fast — binary search on a sorted R for "closest / ≤ target" (sort R first), a hash map of R for "exactly equals target," or two pointers across sorted L and R for "count pairs ≤ K." Extra constraints (exactly n chosen) become buckets on the partials (e.g. by popcount).
