Segment Tree — fast range queries when the array keeps changing

Prefix sums (Lesson 4) answer any range-sum query in O(1), but only on a static array: change one element and you must rebuild the whole prefix array in O(n). The moment a problem mixes point updates with range queries — "add 5 at index i, then tell me the sum of indices l..r, then update again" — prefix sums collapse to O(n) per update. A segment tree is the structure that keeps both operations at O(log n) by storing range aggregates in a balanced tree and touching only the O(log n) nodes on one root-to-leaf path per update. It generalises past sums to any associative combine — min, max, gcd, count — and with lazy propagation it also does range updates in O(log n). The signal is any problem that interleaves updates and range questions, or any offline problem you can reframe as "process in some order while querying a running structure."

2. A balanced binary tree over n leaves (Lesson 16 intuition) has what height, and why does that number keep appearing in "touch one root-to-leaf path" algorithms?

Deriving the segment tree via Range Sum Query - Mutable

Take Range Sum Query - Mutable (LeetCode 307): you're given an array, and must support two operations, interleaved any number of times — update(i, val) sets element i to val, and sumRange(l, r) returns the sum of elements l..r inclusive.

Derive it

Brute force A — recompute each query. Keep the raw array. update is O(1), but every sumRange scans the range in O(n). With q mixed operations that's O(n·q) — too slow when both are large.

Brute force B — prefix sums (Lesson 4). Keep a prefix array so sumRange is O(1). Now the query is free, but update(i, val) invalidates every prefix entry from i onward, forcing an O(n) rebuild. We've just moved the O(n) from queries to updates. Either way, one of the two operations is linear.

Spot the waste. The two extremes fail for the same reason: both store aggregates at one granularity — either per-element (cheap update, expensive query) or whole-prefix (cheap query, expensive update). A range query of length m is answered either by m tiny pieces or by two giant pieces. What we want is pieces of many sizes at once, so any range decomposes into a handful of pre-summed blocks, and any single element lives in only a handful of blocks.

The insight (= the pattern). Build a binary tree of ranges: the root covers [0, n), each node splits its range in half between its two children, and leaves are single elements. Store at every node the sum of its range. There are about 2n nodes and the tree is ⌈log₂ n⌉ tall. Now both operations cost one tree height:

  • Update(i): only the nodes whose range contains i change — that's exactly the single path from leaf i up to the root, log n nodes. Set the leaf, then re-sum each ancestor from its two children. O(log n).
  • Query(l, r): any range [l, r) is covered by O(log n) maximal tree nodes that fall entirely inside it (you never descend into a node already fully contained). Add their stored sums. O(log n).

The win comes from the intermediate granularities the two brute forces lacked: a length-m range is stitched from ≤ 2·log n pre-summed blocks, and each element sits in only log n blocks, so no operation ever touches more than one tree height. That multi-scale decomposition is the segment tree.

# Iterative segment tree, point update + range-sum query.
# Leaves live at t[n .. 2n-1]; internal node i has children 2i and 2i+1.
class SegTree:
    def __init__(self, data):
        self.n = len(data)
        self.t = [0] * (2 * self.n)
        for i in range(self.n):              # place the leaves
            self.t[self.n + i] = data[i]
        for i in range(self.n - 1, 0, -1):   # build parents bottom-up
            self.t[i] = self.t[2*i] + self.t[2*i + 1]

    def update(self, i, val):                # set data[i] = val
        i += self.n
        self.t[i] = val
        i >>= 1
        while i >= 1:                        # walk the one path to the root
            self.t[i] = self.t[2*i] + self.t[2*i + 1]
            i >>= 1

    def query(self, l, r):                   # sum of data[l..r-1], half-open [l, r)
        res = 0
        l += self.n; r += self.n
        while l < r:                         # collect the maximal in-range nodes
            if l & 1: res += self.t[l]; l += 1
            if r & 1: r -= 1; res += self.t[r]
            l >>= 1; r >>= 1
        return res

You didn't recall "segment tree" — you noticed prefix sums buy a fast query only by making updates linear, asked "what if I stored sums at every scale instead of just the whole prefix," and a balanced tree of range-sums fell out. The tree where every node holds its range's aggregate, updated along one path and queried by a handful of maximal blocks, is the pattern.

The transferable shape: the stored value doesn't have to be a sum. Any associative combine works — replace + with min, max, gcd, or "count of values in a range" and the exact same tree answers "min/max/gcd over [l, r)" with point updates. The tree structure is fixed; the monoid you store is the knob. That is why one data structure covers range-sum, range-min (RMQ), and "how many elements so far are less than x" (a counting segment tree over compressed values), which is the engine behind inversion-counting problems.

One more gear: range updates with lazy propagation

The point-update tree makes "change one element" cheap, but some problems want "add 5 to every element in [l, r]" as a single operation. Doing that as r−l+1 point updates is back to O(n). The fix keeps the same tree but adds a lazy value per node: when a range update fully covers a node, record the pending change on that node and stop — don't recurse into its children yet. The deferred change is pushed down only when a later operation actually needs to visit those children. Each range update and range query stays O(log n), because the laziness stops the recursion at the same O(log n) maximal nodes a query would.

Why lazy is correct, in one line

A node's stored aggregate is always kept fully up to date for its own range; the lazy tag only means "my children don't yet know about a uniform change I already folded into my aggregate." As long as you push that tag down before you ever read or split a child, every value you return reflects all updates — you've just delayed the work until it's unavoidable, like a difference-array deferral (Lesson 4) pushed into a tree.

When to reach for a segment tree, and why

  • The array is mutated between queries, and the queries are over ranges. This is the defining case: interleaved update and range-aggregate operations. Prefix sums (Lesson 4) are strictly better when the array is static — O(1) query, no tree — so only reach for a segment tree once updates enter the picture. If there are no updates at all, you're over-engineering.
  • The aggregate is associative — sum, min, max, gcd, or a count — so a parent can be computed from its two children. That is the only requirement on what you store. If the "aggregate" of two ranges can't be formed from their two partial aggregates (it depends on the raw elements in some non-combinable way), a segment tree can't hold it.
  • You need range updates, not just point updates ("add v to all of [l, r]", "assign v to all of [l, r]"). Reach for lazy propagation. The tell is an update phrased over a whole interval rather than a single index; the lazy tag defers the per-element work exactly like a difference array, but inside the tree so queries stay O(log n).
  • An offline problem reframes as "process elements in a chosen order while maintaining a running count/aggregate over a value axis." Counting inversions, "how many later elements are smaller," or "how many seen values fall in a range" become point-update + range-query on a segment tree (or Fenwick tree) indexed by value (coordinate-compressed), not by position. Recognise it when a problem counts order-relations among elements — sort or sweep, and let the tree accumulate.
  • A DP transition needs the max/min/sum of a contiguous band of earlier states. When dp[x] = f(best of dp over some range of earlier values), a segment tree over the state axis turns an O(n) transition scan into O(log n), dropping an O(n²) DP to O(n log n). This is the segment-tree-accelerated-DP composition (see below).

The templates (reproduce from memory)

# ---- Point update, range query (iterative, O(log n) each) ----
class SegTree:
    def __init__(self, data):
        self.n = len(data)
        self.t = [0] * (2 * self.n)
        for i in range(self.n):
            self.t[self.n + i] = data[i]
        for i in range(self.n - 1, 0, -1):
            self.t[i] = self.t[2*i] + self.t[2*i + 1]   # swap + for min/max/gcd
    def update(self, i, val):
        i += self.n; self.t[i] = val; i >>= 1
        while i >= 1:
            self.t[i] = self.t[2*i] + self.t[2*i + 1]
            i >>= 1
    def query(self, l, r):               # half-open [l, r)
        res = 0                          # identity: 0 for sum, +inf for min, -inf for max
        l += self.n; r += self.n
        while l < r:
            if l & 1: res += self.t[l]; l += 1
            if r & 1: r -= 1; res += self.t[r]
            l >>= 1; r >>= 1
        return res

# ---- Range add, range sum (recursive, lazy propagation) ----
class LazySeg:
    def __init__(self, data):
        self.n = len(data)
        self.t = [0] * (4 * self.n)
        self.lazy = [0] * (4 * self.n)
        self._build(1, 0, self.n - 1, data)
    def _build(self, node, lo, hi, data):
        if lo == hi:
            self.t[node] = data[lo]; return
        mid = (lo + hi) // 2
        self._build(2*node, lo, mid, data)
        self._build(2*node+1, mid+1, hi, data)
        self.t[node] = self.t[2*node] + self.t[2*node+1]
    def _push(self, node, lo, hi):                 # flush pending add to children
        if self.lazy[node]:
            mid = (lo + hi) // 2
            for ch, clo, chi in ((2*node, lo, mid), (2*node+1, mid+1, hi)):
                self.lazy[ch] += self.lazy[node]
                self.t[ch]   += self.lazy[node] * (chi - clo + 1)
            self.lazy[node] = 0
    def add(self, l, r, val, node=1, lo=0, hi=None):   # add val to data[l..r]
        if hi is None: hi = self.n - 1
        if r < lo or hi < l: return
        if l <= lo and hi <= r:                    # node fully covered: defer
            self.t[node] += val * (hi - lo + 1)
            self.lazy[node] += val
            return
        self._push(node, lo, hi)
        mid = (lo + hi) // 2
        self.add(l, r, val, 2*node, lo, mid)
        self.add(l, r, val, 2*node+1, mid+1, hi)
        self.t[node] = self.t[2*node] + self.t[2*node+1]
    def query(self, l, r, node=1, lo=0, hi=None):      # sum data[l..r]
        if hi is None: hi = self.n - 1
        if r < lo or hi < l: return 0
        if l <= lo and hi <= r: return self.t[node]
        self._push(node, lo, hi)
        mid = (lo + hi) // 2
        return (self.query(l, r, 2*node, lo, mid)
                + self.query(l, r, 2*node+1, mid+1, hi))

A trap: when "range query" does not mean segment tree

Trap

"Given an immutable array, answer many range-sum queries" (Range Sum Query - Immutable, 303) or "many 2D region-sum queries on a fixed matrix" (Range Sum Query 2D - Immutable, 304). The words "range query, many times" pattern-match to segment tree — but there are no updates. A plain prefix-sum array (Lesson 4) answers each query in O(1) with no tree, no O(log n) factor, and ten lines less code. The segment tree is strictly worse here. The discriminating question is never "are there range queries?" but "does the array change between them?" No mutation → prefix sums; mutation → segment tree. The signal gives candidates; the update-or-not question gives the verdict.

Composition — a Hard built from segment tree + an earlier pattern

Longest Increasing Subsequence II (LeetCode 2407, Hard) — link. Composes this lesson's segment tree (range-max, point update) with the LIS subsequence-DP recurrence (Lesson 33).

Show the decomposition (try it yourself first)

The problem: find the longest strictly increasing subsequence of nums with the extra rule that consecutive picked values differ by at most k (i.e. 1 ≤ nums[i₊₁] − nums[iⱼ] ≤ k).

Pattern A — the LIS DP (Lesson 33): the LIS family's state is "best answer ending at this element." Here it's cleaner to index the DP by value: let dp[v] = length of the longest valid subsequence ending with value v. Processing nums left to right, the element x can extend any subsequence that ended with a value in [x − k, x − 1], so dp[x] = 1 + max(dp[v] for v in [x−k, x−1]). That's the ordinary LIS transition, just with a range of valid predecessors instead of "any smaller value."

The bottleneck: computing max(dp[x−k .. x−1]) by scanning is O(k) per element, so O(n·k) overall — too slow when k is large. This is the exact DP-transition-over-a-band situation from the "when to use" list.

Pattern B — segment tree over the value axis (this lesson): keep a max segment tree indexed by value. The transition becomes one range-max query over [x−k, x−1] (O(log V)); after computing dp[x], do one point update setting position x to max(current, dp[x]) (O(log V)). The O(k) scan collapses to O(log V), turning the O(n·k) DP into O(n log V).

class MaxSeg:                      # point update = "raise", query = range max
    def __init__(self, size):
        self.n = size; self.t = [0] * (2 * size)
    def update(self, i, val):
        i += self.n
        if self.t[i] >= val: return
        self.t[i] = val; i >>= 1
        while i >= 1:
            self.t[i] = max(self.t[2*i], self.t[2*i+1]); i >>= 1
    def query(self, l, r):                     # max over [l, r)
        res = 0; l += self.n; r += self.n
        while l < r:
            if l & 1: res = max(res, self.t[l]); l += 1
            if r & 1: r -= 1; res = max(res, self.t[r])
            l >>= 1; r >>= 1
        return res

def lengthOfLIS(nums, k):
    seg = MaxSeg(max(nums) + 1)                # value axis
    best = 0
    for x in nums:
        prev = seg.query(max(0, x - k), x)     # Pattern A: best dp over [x−k, x−1]
        cur = prev + 1
        seg.update(x, cur)                     # Pattern B: raise dp[x]
        best = max(best, cur)
    return best

The Hard = (LIS subsequence DP: "best ending at value x = 1 + best reachable predecessor") + (segment tree over the value axis to answer "best predecessor in [x−k, x−1]" and record the new value in O(log V)). Strip the "within k" wording and it's plain LIS; the segment tree is only there to make the predecessor lookup fast — which is the recurring role of this structure inside a DP.

Reference card — Segment Tree

When, and why

Use it when an array is mutated between range queries and the aggregate is associative (sum, min, max, gcd, count) so a parent is computable from its two children. It stores range aggregates in a balanced binary tree (~2n nodes, height log n): a point update touches the single leaf-to-root path, and a range query is stitched from O(log n) maximal in-range nodes — both O(log n). If the array never changes, a prefix sum (Lesson 4) is strictly better; the update is the whole reason the tree exists. For range updates ("add/assign v across [l, r]"), add lazy propagation: fold a uniform change into a covered node and defer pushing it to children until something needs them, keeping range-update and range-query at O(log n).

The two shapes

Point update + range query (iterative, array of size 2n): leaves at t[n..2n−1], parent i = combine of t[2i], t[2i+1]; update walks one path up, query folds the maximal nodes while climbing. Range update + range query (recursive, array of size 4n + lazy array): on a fully-covered node record the tag and return; _push flushes the tag to children before any descent. Swap the combine (+ / min / max) and the query identity (0 / +∞ / −∞) to change what it computes.

Template (point update, range sum)

class SegTree:
    def __init__(self, a):
        self.n = len(a); self.t = [0]*(2*self.n)
        for i,x in enumerate(a): self.t[self.n+i] = x
        for i in range(self.n-1,0,-1): self.t[i] = self.t[2*i]+self.t[2*i+1]
    def update(self, i, v):
        i += self.n; self.t[i] = v; i >>= 1
        while i: self.t[i] = self.t[2*i]+self.t[2*i+1]; i >>= 1
    def query(self, l, r):                 # [l, r)
        res = 0; l += self.n; r += self.n
        while l < r:
            if l & 1: res += self.t[l]; l += 1
            if r & 1: r -= 1; res += self.t[r]
            l >>= 1; r >>= 1
        return res
# build O(n); update/query O(log n). min/max: swap + and the identity.
