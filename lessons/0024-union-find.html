Union-Find — the data structure for "are these two connected?"

You can count connected components with DFS (Lesson 21). But when connections arrive one at a time and you must answer "are A and B connected yet?" after each — or you need to detect the exact edge that closes a cycle — repeatedly re-running DFS is wasteful. Union-Find (Disjoint Set Union) maintains connectivity incrementally in nearly constant time per operation. This lesson derives it from that exact waste.

Deriving Union-Find from the waste in repeated DFS

Derive it

The task: edges are given one at a time; after each edge you may be asked "are X and Y in the same connected group?"

Brute force: after each query, run a BFS/DFS from X to see if you can reach Y. That's O(V + E) per query — and with many interleaved unions and queries it degrades to O(Q·(V+E)).

Spot the waste: you keep rediscovering the group structure from scratch, even though adding one edge changes connectivity only slightly (it merges at most two groups). You should maintain the grouping, not recompute it.

The insight (= Union-Find): give every group a single representative ("root"). Store a parent array where each element points toward its group's root. Then:

  • find(x) walks parent pointers up to the root — the root is the group's identity.
  • "Are X and Y connected?" becomes "do find(X) and find(Y) return the same root?"
  • union(X, Y) merges two groups by pointing one root at the other — O(1) structural change.

Making it nearly O(1): two optimizations keep the trees flat. Union by rank/size always attaches the smaller tree under the larger root, so trees stay shallow. Path compression re-points every node visited during a find directly to the root, so future finds are instant. Together they give an amortized cost of α(n) per operation — the inverse Ackermann function, effectively a small constant. So the whole stream of unions and queries runs in almost linear total time.

The deeper principle (so it transfers)

Reach for Union-Find instead of DFS whenever connectivity is dynamic (edges stream in and you must answer "connected?" along the way) or when the question is fundamentally grouping: how many groups, are these two in the same group, which edge first creates a group it shouldn't. DFS answers connectivity for a fixed graph in one shot; Union-Find answers it incrementally and repeatedly, and does it without ever building an explicit adjacency list — it only needs the pairs. The trigger phrase is "merge," "same group," "redundant connection," or "process edges and track components."

When to reach for Union-Find, and why

Connectivity queries interleaved with edge additions

If the problem adds connections over time and asks connectivity questions between them, Union-Find maintains the answer in near-constant time per operation, whereas DFS would recompute everything each query. This "online connectivity" shape is the signature use.

Detecting the edge that creates a cycle in an undirected graph

While adding edges one by one, if both endpoints of the next edge already share a root, that edge connects two already-connected nodes — so it closes a cycle (it is redundant). This gives an elegant O(E·α) cycle detector and is exactly the "redundant connection" family.

Counting or merging groups, especially from pairs

When you're given relationships as pairs (accounts that belong to the same person, stones in the same row/column, equivalent variables) and asked how many distinct groups remain or whether two items are equivalent, Union-Find merges them directly without you ever constructing a graph to traverse.

As the engine of Kruskal's MST (next lesson)

Kruskal's builds a minimum spanning tree by adding the cheapest edges that don't form a cycle — and "doesn't form a cycle" is precisely a Union-Find check. So Union-Find is a prerequisite tool for the MST lesson that follows.

The template (reproduce from memory)

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))   # each element is its own root initially
        self.size = [1] * n            # size of the tree rooted at i
        self.count = n                 # number of disjoint groups

    def find(self, x):                 # with path compression
        root = x
        while self.parent[root] != root:
            root = self.parent[root]
        while self.parent[x] != root:  # re-point every node on the path to root
            self.parent[x], x = root, self.parent[x]
        return root

    def union(self, a, b):             # union by size; returns False if already joined
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False               # same group already -> this edge is redundant
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra           # attach smaller tree under larger root
        self.size[ra] += self.size[rb]
        self.count -= 1                # two groups merged into one
        return True

    def connected(self, a, b):
        return self.find(a) == self.find(b)

Composition — how a Hard is built from this pattern

Number of Good Paths (Hard 2421) composes Union-Find (this lesson) with sorting as a tool (Lesson 11) and hashing (Lesson 5).

Show the decomposition (try it yourself first)

The problem: a tree with a value on each node; count "good paths" — paths whose two endpoints have equal value and where no node on the path exceeds that value.

Piece 1 — sorting as a tool (Lesson 11): process nodes in increasing value order. The key realisation: a good path's endpoints must be the maximum value on that path, so if you only ever union through nodes with value ≤ the current value, any two current-value nodes that become connected can see each other along a valid path.

Piece 2 — Union-Find (this lesson): add each node by unioning it with already-processed neighbours (which, by the sort order, all have value ≤ this node's value). This incrementally grows connected regions "under a ceiling."

Piece 3 — hashing (Lesson 5): within each component, keep a count (a dict root → {value → how many nodes of that value are endpoints-eligible}). When two same-valued nodes land in the same component, the number of new good paths is the product of their counts. Hashing tracks those per-component tallies.

Why brute force is worse: checking every pair of equal-valued nodes and validating the path is O(N²) or worse; sort + union + per-component counting is about O(N log N · α).

Reference card — Union-Find (DSU)

The compressed version.

When and why

Use it for dynamic connectivity (edges stream in; answer "same group?" along the way), undirected cycle detection (an edge whose endpoints already share a root closes a cycle), and grouping from pairs (count groups / check equivalence without building a graph). It's also the engine of Kruskal's MST. DFS handles a fixed graph once; DSU handles it incrementally in near-constant time per op.

The idea

Each group has one root. find(x) walks to the root; two items are connected iff they share a root; union points one root at another. Union by size keeps trees shallow; path compression re-points visited nodes straight to the root. Together → amortized α(n) per operation (effectively constant).

Template (core ops)

parent = list(range(n)); size = [1]*n
def find(x):
    while parent[x] != x:
        parent[x] = parent[parent[x]]   # path halving
        x = parent[x]
    return x
def union(a, b):
    ra, rb = find(a), find(b)
    if ra == rb: return False           # redundant edge / already connected
    if size[ra] < size[rb]: ra, rb = rb, ra
    parent[rb] = ra; size[ra] += size[rb]
    return True
