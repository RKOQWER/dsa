Tree DFS — deriving "what do I ask my children, and what do I tell my parent?"

Almost every binary-tree problem is solved by one question asked at each node: "what information do I need back from my left and right subtrees, and what single piece of information do I return to my own parent?" By the end you'll turn a cold tree problem into that question automatically, and know when the answer must be a value you return versus a running best you track on the side.

Deriving tree DFS from scratch

Take maximum depth of a binary tree. A tree is self-similar (Lesson 14): each child is itself a tree. So recursion is the natural fit — the only real question is what each call returns.

Derive it

Frame it as the node's-eye view: stand at one node. You cannot see the whole tree, but you can ask each child subtree a question and trust the answer (the leap of faith from Lesson 14). What do you ask? "How deep are you?" If the left subtree is depth L and the right is depth R, then your depth is 1 + max(L, R) — one for yourself, plus the deeper child. Base case: an empty subtree has depth 0.

def maxDepth(node):
    if not node:               # base: empty subtree
        return 0
    L = maxDepth(node.left)    # ask left child
    R = maxDepth(node.right)   # ask right child
    return 1 + max(L, R)       # combine into MY answer, hand up

That's the entire pattern. The hard part of any tree problem is never the recursion plumbing — it's answering the two design questions: what do I ask my children, and what do I return to my parent. Get those two right and the code writes itself.

Top-down vs bottom-up — the real distinction

Both directions are DFS; they differ in when a node does its work relative to visiting its children.

  • Bottom-up (post-order): you recurse into the children first, then combine their returned values into your own answer. This is the common case — max depth, "is this subtree balanced", diameter, subtree sums. Information flows upward. You use it whenever a node's answer depends on facts about its subtrees.
  • Top-down (pre-order): you compute something for the current node before recursing, and pass it down as an argument. You use it when a node's answer depends on the path from the root — for example "is this node's value the max along the root-to-here path" (Count Good Nodes), where you carry the running max downward.

The technique that unlocks the hard tree problems: return one thing, track another

Some problems ask for a quantity that is not the same thing each node needs to report upward. The classic is diameter (longest path between any two nodes). Here is the subtlety that confuses everyone, stated plainly:

The split between "answer" and "return value"

A node's contribution to a path that goes through it and bends is leftHeight + rightHeight — but that bent path cannot be extended by the parent (a parent can only attach to a straight downward arm). So the node must return the straight arm it can offer upward, 1 + max(left, right), while recording the bent path left + right into a shared "best so far" on the side. One value goes up for the parent to use; a different value updates the global answer.

def diameterOfBinaryTree(root):
    best = 0
    def height(node):
        nonlocal best
        if not node:
            return 0
        L = height(node.left)
        R = height(node.right)
        best = max(best, L + R)       # bent path THROUGH this node (the answer)
        return 1 + max(L, R)          # straight arm handed to the parent
    height(root)
    return best

Recognizing "the thing I report to my parent differs from the thing I'm optimizing globally" is the single most transferable idea in tree DFS. It reappears in maximum path sum, longest univalue path, and the "longest zigzag" problems.

When to reach for tree DFS, and why it works

Reach for DFS on any problem over a tree (or a structure you can treat as a tree) where a node's answer is built from facts about its subtrees — heights, sums, counts, "does every subtree satisfy X", lowest common ancestor, path sums. The tell is simply that the data is a tree and you're asked for a global property, a per-node property, or an existence check. It works because a tree is defined recursively — each node owns two smaller trees — so a single recursive function that handles one node and trusts the recursion on its children covers the entire tree in one O(n) pass, visiting each node exactly once.

Prefer bottom-up when the node's answer needs its subtrees' answers (most problems); prefer top-down when the answer needs root-to-node path context carried downward. Use the return-one-track-another split when the quantity you optimize globally (a bent path through a node) is not the quantity a parent can reuse (a straight arm). If the tree is a BST, the extra ordering property unlocks sharper techniques — that's the next lesson (Lesson 18).

Composition — how a Hard is built from this pattern

Path Sum III (Medium 437) — link — composes tree DFS (this lesson) with the prefix-sum + hashmap idea (Lessons 4 and 5). It's labelled Medium but the composition is genuinely hard; it's the cleanest showcase of stacking two earlier patterns. Try it before opening the decomposition.

Show the decomposition (try it yourself first)

Count downward paths (not necessarily root-to-leaf) whose values sum to a target. Brute force: from every node, walk every downward path and sum — O(n²) or worse.

Piece A (prefix sum + hashmap, Lessons 4 & 5): recall the array trick "number of subarrays summing to k" — keep a running prefix sum and a hashmap of how many times each prefix value has occurred; a subarray summing to k exists wherever prefix − k was seen before. That is the exact same counting idea.

Piece B (tree DFS, this lesson): apply that counting along each root-to-current path instead of an array. DFS downward carrying the running prefix sum and the hashmap of prefix counts seen on the current path; at each node add count[prefix − target]. The twist unique to trees: you must undo the current node's prefix from the map as you return (the do/recurse/undo rhythm from Lesson 15), so a path only counts prefixes that are actually its ancestors.

def pathSum(root, target):
    count = {0: 1}          # prefix-count hashmap (Lessons 4 & 5)
    total = 0
    def dfs(node, prefix):
        nonlocal total
        if not node: return
        prefix += node.val
        total += count.get(prefix - target, 0)   # paths ending here
        count[prefix] = count.get(prefix, 0) + 1  # do
        dfs(node.left, prefix)
        dfs(node.right, prefix)
        count[prefix] -= 1                         # undo (leave the path)
    dfs(root, 0)
    return total

The Hard = (prefix-sum/hashmap counting) + (tree DFS carrying state down with an undo on the way back up). Both pieces you already own. Name the pieces and the Hard stops being hard.

Reference card — Tree DFS

The compressed version. A 2-minute re-read should reload the whole pattern.

When to use it, and why

Use on any tree problem where a node's answer is built from facts about its subtrees (heights, sums, counts, balance, LCA, path sums), or needs root-to-node path context. It works because a tree is recursively defined — one function handling a single node and trusting the recursion on its children visits every node once, O(n).

The two design questions (ask these first)

  • What do I ask my children? (the recursive return from each subtree)
  • What do I return to my parent? (the one value combining myself + children)

Top-down vs bottom-up

Bottom-up (post-order): recurse first, then combine children's returns — the common case. Top-down (pre-order): compute for the node, pass context down as an argument — for root-to-node path problems.

Return-one-track-another (unlocks the hards)

When the quantity you optimize globally (e.g. a bent path through a node, L + R) differs from what a parent can reuse (a straight arm, 1 + max(L, R)), return the arm and update a shared best on the side. Core of diameter, max path sum, longest univalue path.

Template

def dfs(node):
    if not node: return base
    L = dfs(node.left); R = dfs(node.right)
    best = max(best, combine_through(node, L, R))  # the answer (side)
    return extend_upward(node, L, R)               # for the parent
